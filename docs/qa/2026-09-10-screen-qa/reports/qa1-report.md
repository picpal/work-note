## FAIL 상세

### [FAIL-1] 감사 로그가 2FA·개인정보·첨부·설정·템플릿 행위를 한글 라벨/필터에서 누락
- 화면/경로: admin.html → 감사 로그 (`frontend/src/admin/mappers.ts` `ACTS` / `KNOWN_ACTS`)
- 재현 절차:
  1) admin으로 로그인해 2FA를 등록한다(프로필 → 2단계 인증 → 등록 확인).
  2) 로그아웃 후 다시 로그인해 2FA 코드를 입력한다.
  3) admin.html → 감사 로그를 연다.
  4) 목록 상단의 "행위" 열과, "전체 행위" 드롭다운 목록을 본다.
- 기대: 다른 행위처럼 한글 라벨(예: "2FA 등록", "2FA 인증 성공", "2FA 인증 실패")로 표시되고, 드롭다운에서 해당 행위만 필터할 수 있어야 한다.
- 실제: `2fa.setup` / `2fa.enabled` / `2fa.challenge` / `2fa.verify.success` / `2fa.recover.request` 처럼 **원시 코드가 그대로 노출**되고, 드롭다운(35종)에는 이 행위들이 아예 없어 필터 불가.
  백엔드가 기록하는 코드와 UI 라벨 맵을 대조하면 누락은 2FA만이 아니다:
  - 2FA 12종: `2fa.setup` `2fa.enabled` `2fa.disabled` `2fa.disable.blocked` `2fa.admin.reset` `2fa.challenge` `2fa.verify.success` `2fa.verify.fail` `2fa.locked` `2fa.recover.request` `2fa.recover.success` `2fa.recover.fail`
  - 계정 잠금: `login.locked`
  - 첨부: `attachment.add` `attachment.remove`
  - 개인정보: `pii.request` `pii.approve` `pii.reject` `pii.notice` (`pii.view`는 라벨은 있으나 드롭다운에는 없음 → 필터 불가)
  - 설정/연동: `settings.upload` `settings.redmine` `redmine.import` `redmine.token.set` `redmine.token.delete`
  - 템플릿: `template.system.create` `template.system.update` `template.system.delete`
- 영향: 이 화면은 스스로 "ISMS · PCI-DSS 추적용"이라고 표시한다. 그런데 보안 담당자가 실제로 뽑아야 하는 이벤트 —
  **2FA 인증 실패·계정 잠금·2FA 관리자 초기화·개인정보 열람 승인** — 이 전부 필터 불가이고 화면에서는 영문 코드로 보인다.
  월간 감사 리포트도 `isAdminAction()`이 `2fa.admin.reset`만 예외 처리하므로 나머지 2FA 사건은 "관리자 작업"에도 잡히지 않는다.
- 심각도: 중간 (기능은 동작하나 보안 감사 목적 자체가 부분적으로 무력화됨)

## UX/UI 개선 제안

### [UX-1] 공유 링크 생성 시 미저장 본문이 반영되지 않아 수신자가 빈 노트를 본다
- 화면: index.html — 에디터 + 공유 모달
- 현재 동작: 본문/제목은 1분 디바운스 PATCH로 저장된다. 공유 링크 생성(POST /nodes/{id}/share)은 이 flush를 트리거하지 않는다.
- 문제: QA 중 실제로 재현됐다. 노트를 만들고 본문을 입력한 직후 공유 링크를 만들어 열었더니 제목은 "제목 없는 노트", 본문은 비어 있었고, 첨부만 보였다.
  약 1분 뒤 디바운스가 발화한 뒤에야 정상 렌더됐다. 링크를 만든 사람은 이미 복사해서 전달한 상태이므로, 수신자는 "빈 노트"를 보고 되돌아온다.
- 제안: 공유 링크 생성 직전에 pending write를 강제 flush(Cmd+S와 같은 경로)하고, flush 실패 시 "저장되지 않은 변경이 있습니다" 경고 후 생성 여부를 묻는다.
- 우선순위: 높음

### [UX-2] 2FA 복구 코드 발송이 SMTP 미설정 시 조용히 아무 일도 하지 않는다
- 화면: login.html → 2단계 인증 → 복구 코드로 로그인
- 현재 동작: `RecoveryService.request()`가 `if (!mail.available()) return;` 으로 즉시 반환한다(계정 열거 방지를 위한 균등 응답). 화면은 그대로 "복구 코드 입력"으로 넘어간다.
- 문제: 폐쇄망에서 SMTP를 안 붙인 채 배포하면(이 QA 환경이 그렇다) 사용자는 오지 않을 메일을 기다리고, "코드 재발송"을 반복하다 결국 관리자에게 문의하는 것 말고는 길이 없다. 화면 어디에도 "이메일 복구가 꺼져 있음"을 알리는 단서가 없다.
- 제안: SMTP 미설정은 계정별 정보가 아니라 서버 전역 사실이므로 열거 위험이 없다. 복구 진입 시점(또는 `GET /auth/2fa/recover/available`)에 "이 서버는 이메일 복구가 비활성화되어 있습니다 — 관리자에게 2FA 초기화를 요청하세요"를 안내하고 발송 버튼을 감춘다.
- 우선순위: 중간

### [UX-3] 공유 링크의 "로그인하러 가기"가 원래 링크로 돌아오지 않는다
- 화면: share.html (pin 링크를 비로그인 상태로 열었을 때)
- 현재 동작: 안내문이 "로그인한 뒤 이 링크를 다시 열어주세요"라고 적혀 있고, 버튼은 login.html로만 이동한다. 로그인 후에는 index.html로 간다.
- 문제: 수신자는 로그인을 마친 뒤 메일/메신저로 돌아가 원래 링크를 다시 찾아 눌러야 한다. 모바일에서 링크를 잃어버리면 다시 요청해야 한다.
- 제안: `login.html?next=/share.html?token=…` 로 복귀 경로를 넘기고, 로그인 성공 후 해당 경로로 리다이렉트한다(next는 same-origin 상대경로만 허용).
- 우선순위: 중간

### [UX-4] 공유 링크 취소가 되돌릴 수 없는데 확인 절차가 화면마다 다르다
- 화면: index.html 공유 모달 / admin.html 공유 링크
- 현재 동작: 공유 모달은 "복사" 바로 옆의 "취소" 버튼을 누르는 즉시 확인 없이 취소된다. 관리자 화면은 브라우저 네이티브 `confirm()`을 띄운다.
- 문제: (a) 공유 모달에서 "복사"와 "취소"는 나란히 붙은 같은 크기의 버튼이라 오조작 위험이 크고, 취소된 링크는 되살릴 수 없어 새 링크를 만들어 다시 배포해야 한다.
  (b) 관리자 화면의 네이티브 다이얼로그는 모노톤 디자인·다크 모드와 이질적이고 "qa1.localhost:8341 says" 같은 출처 문구가 그대로 보인다. 앱의 다른 확인(가입 승인 등)은 자체 모달을 쓴다.
- 제안: 두 화면 모두 앱 확인 모달로 통일하고, 취소 직후 토스트에 "실행 취소"(짧은 시간 내 재발급) 또는 최소한 "새 링크 만들기" 바로가기를 제공한다.
- 우선순위: 중간

### [UX-5] 오류 토스트가 1.5초 만에 사라진다
- 화면: 전역 (`App.tsx` `TOAST_MS = 1500`)
- 현재 동작: 성공/실패 구분 없이 모든 토스트가 1.5초 후 사라진다.
- 문제: 공유 링크 생성 실패 메시지("만료 일수는 1~365 사이여야 합니다: 0")처럼 원인·조치가 담긴 문장을 1.5초 안에 읽어야 한다. QA 중 1.8초 뒤에 화면을 봤을 때는 이미 사라져서 "아무 반응이 없다"고 오인했다. 실제 사용자도 같은 오해를 한다.
- 제안: 실패 토스트는 4~5초로 늘리고 닫기 버튼을 둔다. 폼에서 발생한 오류는 프로필 화면처럼 인라인으로 남기는 편이 더 낫다(같은 앱 안에 이미 두 방식이 공존한다).
- 우선순위: 중간

### [UX-6] 보안 설정 화면에 2FA 정책이 전혀 나오지 않는다
- 화면: admin.html → 보안 설정
- 현재 동작: 비밀번호 정책·해시·세션 타임아웃·가입 승인·감사 기록만 읽기 전용으로 보여준다. 2FA 관련 항목은 한 줄도 없다.
- 문제: 이 제품의 2FA는 "관리자 강제 + 유예 기간 + 일반 사용자 opt-in"이라는 비자명한 정책인데, 관리자는 그 정책이 무엇인지, 유예가 며칠인지, 몇 명이 등록했는지를 이 화면에서 확인할 수 없다. 감사 대응 시 코드를 열어봐야 한다.
- 제안: 읽기 전용이라도 "2단계 인증: 관리자 필수(유예 N일) · 일반 사용자 선택" 행과 "등록 완료 n / 전체 m" 요약을 추가한다(사용자별 상태는 이미 사용자 관리에 있다).
- 우선순위: 중간

### [UX-7] 관리자 공유 링크 화면이 만료·취소된 링크를 보여주지 않는다
- 화면: admin.html → 공유 링크
- 현재 동작: "활성 링크 일괄 조회·취소"만 제공한다. 취소하면 목록에서 사라지고, 만료된 링크도 나오지 않는다. 상태 컬럼이 없다.
- 문제: "지난주에 만든 그 링크가 아직 살아 있나?"를 확인할 방법이 목록에 없다. 사라진 링크가 만료된 것인지, 누가 취소한 것인지, 원래 없었던 것인지 구분되지 않아 감사 로그를 따로 뒤져야 한다.
- 제안: 상태 컬럼(활성/만료/취소)과 기간 필터를 추가하고, 취소된 행은 취소자·취소 시각과 함께 회색 처리로 남긴다.
- 우선순위: 중간

### [UX-8] "지금 등록" 배너를 눌러도 2FA 섹션으로 가지 않는다
- 화면: index.html 상단 관리자 2FA 유예 배너 → 프로필 모달
- 현재 동작: 배너의 "지금 등록"은 프로필 모달을 열지만 최상단(프로필 정보)에 착지한다. 2FA 섹션은 모달 맨 아래라 스크롤해야 보인다.
- 문제: 사용자는 "2FA를 등록하라"는 지시를 따라 눌렀는데 이름/이메일 폼을 보게 된다. 모달이 화면 높이를 넘겨서 2FA 섹션은 첫 화면에서 잘려 있다.
- 제안: 배너에서 열 때는 2FA 섹션으로 스크롤(또는 `TotpEnrollGate`처럼 2FA 전용 모달로 진입)한다.
- 우선순위: 낮음

### [UX-9] 좁은 화면에서 로그인 카드 오른쪽이 잘린다
- 화면: login.html (share.html의 안내 카드도 같은 패턴)
- 현재 동작: `.auth { padding: 24px }` 안에 `.auth-card { width: min(400px, 94vw) }`. 390px에서 카드 너비 366.6px > 콘텐츠 폭 342px이라 그리드 안전 정렬이 start로 떨어져 왼쪽 24px, 오른쪽 0이 된다(카드 오른쪽 끝 390.6px).
- 문제: 390px에서 이미 좌우 여백이 24px : 0으로 어긋나고, 320px(구형 단말·창 분할)에서는 카드 오른쪽 테두리와 라운드가 화면 밖으로 잘려 "레이아웃이 깨진 화면"으로 보인다. 가로 스크롤은 생기지 않아 사용자는 원인을 알기 어렵다.
- 제안: `width: min(400px, 100%)` 로 바꾸어 컨테이너 패딩이 좌우 여백을 담당하게 한다(또는 카드 폭 계산에서 패딩을 빼고 `calc(100vw - 48px)` 사용).
- 우선순위: 낮음

## 환경 메모 (앱 결함 아님)

- **다중 QA 서버 세션 충돌**: QA1~QA4가 각각 8341~8344 포트로 **같은 브라우저**에서 `localhost`를 쓰는데, 쿠키는 포트를 구분하지 않는다.
  Tomcat `JSESSIONID`가 호스트 `localhost` 하나로 공유되어, 다른 테스터가 로그인하면 내 세션이 덮여 401 → 로그인 화면으로 튕겼다(초반에 3회 발생).
  이후 `http://qa1.localhost:8341`(같은 루프백, 별도 쿠키 호스트)로 전환해 격리했고 이후 재발하지 않았다. **폐쇄망 실배포는 서버가 하나이므로 앱 결함이 아니다.**
- **SMTP 미설정**: 이 QA 서버에는 `WORKNOTE_SMTP_HOST`가 없어 `NoopMailSender`가 동작한다. A8의 복구 코드 실제 수신·검증은 검증 불가(UI 전환만 확인). 관련 UX 문제는 [UX-2].
- **네이티브 다이얼로그**: E5의 `confirm()`이 뜨면 ego-browser의 페이지 평가가 블록된다. 다이얼로그가 실제로 뜨는 것을 확인한 뒤, 자동화 진행을 위해 `window.confirm`을 true 반환으로 대체하고 취소 동작을 검증했다.
- **관리자 2FA는 해제 불가(정상 동작)**: QA 종료 후 원복하려 했으나 프로필 → `2FA 비활성화`는 "관리자는 2FA를 비활성화할 수 없습니다"로 차단된다(`2fa.disable.blocked` 설계대로).
  따라서 **8341 서버의 admin 계정은 현재 2FA가 켜져 있다.** 후속 테스터가 로그인하려면 TOTP 시크릿 `BV73W264QT57OO3KDWMZIYTNO6GEJBIW` 을 인증 앱에 넣거나,
  DB(`frontend/e2e/.runtime-8341/wn.db`)를 초기화하고 서버를 재기동하면 된다.
- **QA 중 생성한 데이터**: 사용자 `qa1-tester`(방문자, 승인됨), 노트 `시작하기/QA1 첨부 공유 렌더`(첨부 qa1-sample.png + 인라인 이미지), 활성 공유 링크 2건, 취소된 공유 링크 2건.
