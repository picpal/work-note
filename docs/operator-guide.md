## 1. 아키텍처 개요

```
┌─────────────── worknote-0.1.0.jar (단일 프로세스) ───────────────┐
│  Spring Boot 3.5 (내장 Tomcat, :8080)                            │
│  ├─ /            프런트엔드 정적 파일 (jar에 포함된 dist)          │
│  └─ /api/*       REST API (세션 인증 · 권한 엔진 · 감사)           │
│  Flyway ── 기동 시 스키마 자동 마이그레이션                        │
└──────────────────────────────────────────────────────────────────┘
        │                              │
   SQLite 파일                    첨부 디렉토리
   WORKNOTE_DB                    WORKNOTE_UPLOAD_DIR
   (기본 ./worknote.db)           (기본 ./attachments)
```

- 외부 의존 서비스 없음(CDN·외부 API 0). 폐쇄망에서 그대로 동작합니다.
- SQLite는 단일 라이터 특성상 커넥션 풀이 1로 고정되어 있습니다(`SQLITE_BUSY` 방지). 3~4팀 규모를 상정한 설계입니다.
- 데이터는 **DB 파일 + 첨부 디렉토리** 두 곳뿐입니다. 백업도 이 둘이 전부입니다.

## 2. 설치와 기동

### 요구사항

- Java 21 (빌드·실행)
- Node.js + pnpm (빌드 시에만)

### 빌드

```bash
cd frontend && pnpm install && pnpm build   # dist/ 생성 (jar에 포함됨 — 선행 필수)
cd ../backend && ./gradlew bootJar          # build/libs/worknote-0.1.0.jar
```

### 기동

```bash
# local 모드 (무인증 — 개인 PC용)
java -jar worknote-0.1.0.jar

# server 모드 (인증 + 권한 — 팀 공용)
# 저장 디렉토리 준비 — 없으면 앱이 700으로 만들지만, 소유자를 맞춰 미리 만드는 편이 확실합니다.
install -d -m 700 -o worknote -g worknote /data/worknote

WORKNOTE_MODE=server \
WORKNOTE_ADMIN_PASSWORD='10자-이상-초기-관리자-비밀번호' \
WORKNOTE_DB=/data/worknote/worknote.db \
WORKNOTE_UPLOAD_DIR=/data/worknote/attachments \
WORKNOTE_2FA_KEY="$(openssl rand 32 | base64)" \
java -jar worknote-0.1.0.jar
```

- server 모드 **최초 기동** 시 사용자가 0명이면 `admin` 계정(사번 `admin`, 역할 `admin`)이 `WORKNOTE_ADMIN_PASSWORD`로 자동 생성됩니다. 비밀번호가 비어 있으면 기동이 실패합니다(fail-secure).
- 이후 기동에서는 부트스트랩이 건너뛰어지므로 `WORKNOTE_ADMIN_PASSWORD`는 더 이상 필요 없습니다.
- **`WORKNOTE_2FA_KEY`는 한 번 정하면 바꾸지 마세요.** 이 키로 2FA 시드와 Redmine API 키가 암호화됩니다. 키를 바꾸거나 잃으면 기존 등록이 전부 복호 불가가 되어 사용자 전원이 재등록해야 합니다. 키 파일을 안전한 곳에 별도 보관하세요.

### 환경변수

| 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `WORKNOTE_MODE` | `local` | `local`(무인증) / `server`(인증+권한) |
| `WORKNOTE_DB` | `./worknote.db` | SQLite 파일 경로. **server 모드에서는 절대 경로 필수** — 기본값은 상대 경로라 그대로 두면 기동 실패 |
| `WORKNOTE_STORAGE_STRICT` | `true` | 저장소 권한 점검 실패 시 server 모드 기동을 중단할지. `false`면 WARN만 남기고 계속 기동 — [데이터 파일 권한](#데이터-파일-권한)의 탈출구이며, 문제 자체를 없애지는 않음 |
| `WORKNOTE_ADMIN_PASSWORD` | (없음) | server 모드 **최초 기동 시 필수**. 초기 admin 비밀번호(10자 이상) |
| `WORKNOTE_UPLOAD_DIR` | `./attachments` | 첨부 바이너리 저장 루트 |
| `WORKNOTE_PURGE_RETENTION_DAYS` | `30` | 휴지통 보존 일수. 0 이하 = 자동 영구 삭제 끔 |
| `WORKNOTE_ATTACHMENT_REAP_GRACE_HOURS` | `0`(끔) | 행 없는 첨부 파일(고아) 회수 유예 시간. 양수로 켜는 것은 **업로드 루트가 앱 전용**이라는 단언입니다 — 켜기 전 [고아 첨부 파일 회수](#고아-첨부-파일-회수-선택-기능--기본-꺼짐) 필독 |
| `WORKNOTE_2FA_KEY` | (없음) | Base64(32바이트) AES-256 키. 2FA·Redmine 키 암호화에 사용. `openssl rand 32 \| base64`로 생성 |
| `WORKNOTE_SMTP_HOST` | (없음) | 2FA 복구 코드 메일 발송용 SMTP 서버. 미설정 시 복구 메일 기능 비활성 |
| `WORKNOTE_SMTP_PORT` | `25` | SMTP 포트 |
| `WORKNOTE_SMTP_FROM` | `worknote@corp.local` | 발신 주소 |
| `WORKNOTE_SMTP_USER` / `WORKNOTE_SMTP_PASSWORD` | (없음) | SMTP 인증 계정(필요 시) |
| `WORKNOTE_SMTP_STARTTLS` | `false` | STARTTLS 사용 여부 |
| `SERVER_PORT` | `8080` | 서비스 포트 (`--server.port=` 인자도 가능) |
| `WORKNOTE_TLS_ENABLED` | `false` | **TLS 스위치.** `true`면 HTTPS로 기동. 자재(키스토어·번들·PEM) 없이 켜면 기동 실패 |
| `WORKNOTE_TLS_KEYSTORE` | (없음) | PKCS12 키스토어 경로. 이걸 지정하고 `WORKNOTE_TLS_ENABLED`를 켜지 않으면 **기동 실패**(평문으로 뜨면서 TLS라 착각하는 사고 방지) |
| `WORKNOTE_TLS_KEYSTORE_PASSWORD` | (없음) | 키스토어 비밀번호 |
| `WORKNOTE_TLS_KEYSTORE_TYPE` | `PKCS12` | 키스토어 형식(`JKS`도 가능하나 PKCS12 권장) |
| `WORKNOTE_TLS_KEY_ALIAS` | `worknote` | 키스토어 안의 키 별칭. 변환 시 `-name`으로 지정한 값과 맞추세요 |
| `WORKNOTE_CANONICAL_ORIGIN` | (없음) | CSRF Origin 검증의 비교 기준(예: `https://note.domain.co.kr`). **리버스 프록시가 TLS를 종단하면 필수** — 아래 참조 |
| `SERVER_FORWARD_HEADERS_STRATEGY` | (없음) | 프록시 뒤에서 `X-Forwarded-*`를 신뢰하려면 `framework` |

고정 정책(환경변수 아님): 세션 타임아웃 30분, 멀티파트 업로드 상한 64MB(실 정책은 관리자 콘솔의 업로드 정책이 우선), 세션 쿠키 `HttpOnly` + `SameSite=lax`. 쿠키 `Secure`는 **설정할 필요가 없습니다** — TLS 활성 여부에서 자동으로 유도됩니다([TLS 적용](#tlshttps-적용) 참조).

### 데이터 파일 권한

기동 시 앱이 스스로 저장소 권한을 맞춥니다(POSIX 파일시스템에 한함. Windows에선 경고만 남기고 건너뜁니다 — OS ACL로 직접 제한하세요).

| 대상 | 권한 | 비고 |
| --- | --- | --- |
| DB 파일의 **부모 디렉토리** | `700` | SQLite가 실행 중 만드는 `-wal`/`-shm`/journal까지 한 번에 덮는 통제 지점 |
| DB 파일 | `600` | 이미 있으면 기동 시 보정, 새로 만들어지면 스키마 초기화 직후 보정 — 어느 쪽이든 최종 `600` |
| 업로드 루트(`WORKNOTE_UPLOAD_DIR`) | `700` | 없으면 그 권한으로 생성 |
| 첨부 파일·샤딩 디렉토리 | `600` / `700` | **생성 시점에** 부여(넓게 만든 뒤 조이지 않음) |

원칙은 두 가지입니다.

1. **앱이 만든 것만 앱이 바꿉니다.** 디렉토리가 없으면 `700`으로 만들지만, **이미 존재하는 디렉토리의 권한은 바꾸지 않습니다**. 대신 server 모드에서 그 디렉토리가 그룹·타인에게 열려 있으면 기동을 중단하고 실행할 `chmod` 명령을 알려줍니다.
2. **권한을 바꾸는 곳은 심볼릭 링크를 거부하고, 검증만 하는 곳은 링크를 해석합니다.** 실제로 권한을 바꾸는 지점은 DB 파일(`600`) 하나뿐이라 거기서만 링크를 거부합니다. 디렉토리는 권한을 바꾸지 않으므로 링크를 그대로 허용하고 실경로를 기준으로 검증합니다 — 별도 볼륨을 링크로 붙인 배치가 깨지지 않습니다.

server 모드는 여기에 더해 **`WORKNOTE_DB`가 절대 경로일 것**을 요구합니다. 상대 경로는 프로세스를 어느 디렉토리에서 띄웠는지에 따라 DB 위치가 달라져 전용 저장소라고 볼 수 없기 때문입니다. 기본값 `./worknote.db`도 상대 경로이므로, **`WORKNOTE_DB` 없이 server 모드로 띄우면 기동이 실패합니다.**

local 모드(개인 PC·무인증)는 위 검증을 하지 않고 경고만 남긴 뒤 계속 기동합니다 — 무설정으로 그냥 동작해야 하기 때문입니다.

#### `WORKNOTE_STORAGE_STRICT` — 기동을 막지 않는 탈출구

기본값은 `true`(fail-closed)입니다. `WORKNOTE_STORAGE_STRICT=false`로 두면 server 모드에서도 위 점검 결과를 **WARN 로그로 남기고 기동을 계속**합니다.

- **정당한 용도**: 백업 계정 등에 그룹 접근을 의도적으로 열어 둔 배포처럼, 점검을 통과할 수 없지만 그 상태가 의식적 결정인 경우.
- **하지 않는 일**: 노출을 없애 주지 않습니다. 디렉토리는 여전히 그룹·타인에게 열려 있고, DB에는 노트 본문과 개인정보가 그대로 들어 있습니다.
- **매 기동 WARN이 뜨는 것은 의도된 동작입니다.** 로그를 조용하게 만들려고 켜는 옵션이 아니라, "이 배포는 소유자 전용이 아니다"를 계속 남기는 옵션입니다. 로그 수집 대상에서 제외하지 마세요.
- **적용 범위**: 디렉토리 권한 지적뿐 아니라 **절대 경로 요구도 함께 WARN으로 내려갑니다**(같은 점검 목록입니다). 그래도 `WORKNOTE_DB`는 절대 경로로 지정하세요 — 경로가 실행 위치에 따라 달라지는 문제는 권한과 무관하게 "DB가 비어 있다"류의 사고로 이어집니다.

> #### ⚠️ 업그레이드 시 server 모드 기동이 막히는 경우
>
> **이전 릴리스에는 저장소 권한 점검이 아예 없었습니다.** 앱이 DB·첨부 디렉토리의 권한을 바꾸지도, 검사하지도 않았습니다. 이번 버전에서 그 점검이 처음 들어오므로, 지금까지 아무 문제 없이 돌던 배포도 **업그레이드 후 기동이 실패할 수 있습니다.** 재기동 전에 아래를 먼저 확인하세요.
>
> | 상황 | 조치 |
> | --- | --- |
> | **`WORKNOTE_UPLOAD_DIR`가 이미 있고 `755` 등으로 열려 있음** | 앱 전용 디렉토리임을 확인한 뒤 `chmod 700 <dir>` (아래 "chmod 전 확인" 참조). **umask 022로 만든 디렉토리는 전부 755이므로 기존 server 배포 대부분이 여기 걸립니다** |
> | `WORKNOTE_DB` 미지정(기본 `./worknote.db`) 또는 **상대 경로** | 전용 디렉토리로 DB를 이전하고 `WORKNOTE_DB=/var/lib/worknote/worknote.db` 지정 (아래 "DB 이전 절차" 참조) |
> | DB 부모 디렉토리가 이미 있고 `755` 등으로 열려 있음 | 앱 전용 디렉토리면 `chmod 700 <dir>`, 다른 용도와 공유하는 디렉토리면 **이전** |
> | `WORKNOTE_DB=/tmp/worknote.db` 처럼 **공용 디렉토리** | **`chmod 700 /tmp`를 실행하지 마세요** — 호스트의 다른 프로그램이 전부 깨집니다. 전용 디렉토리로 이전하세요 |
> | `WORKNOTE_DB`가 **심볼릭 링크 파일** | 링크가 아닌 실제 파일 경로를 지정. SQLite가 `-wal`을 링크 옆에 두는지 타깃 옆에 두는지가 구현 의존이라 보호 보장이 깨집니다 |
> | DB 부모·업로드 루트 자리에 **디렉토리가 아닌 항목** | 해당 환경변수에 앱 전용 디렉토리 경로를 지정 |
>
> **`WORKNOTE_DB`에 상대 경로를 막는 이유**는 DB 위치가 프로세스를 띄운 작업 디렉토리에 따라 달라지기 때문입니다. 공용 서버에서 그런 경로는 전용 저장소가 아니고(기동 스크립트나 systemd `WorkingDirectory`가 바뀌면 다른 파일을 보게 됩니다), 그 부모를 하드닝해도 되는지 판단할 근거도 없습니다. 앱은 기존 디렉토리의 권한을 **바꾸지 않습니다** — 검증만 하고 기동을 세웁니다.
>
> ##### chmod 전 확인 — 앱 전용 디렉토리일 때만
>
> `chmod 700`은 **그 디렉토리가 WorkNote 전용일 때만** 올바른 조치입니다. 다른 서비스·사용자와 함께 쓰는 디렉토리라면 chmod하지 말고 WorkNote 데이터를 전용 디렉토리로 **이전**하세요. 심볼릭 링크에 chmod하면 링크가 아니라 **링크가 가리키는 실제 디렉토리**의 권한이 바뀌므로, 공유 볼륨을 가리키는 링크에 실행하면 그 볼륨 전체가 영향을 받습니다.
>
> ```bash
> ls -ld /data/worknote            # 소유자·권한 확인
> ls -ld $(readlink -f /data/worknote)   # 링크면 실제 대상 확인
> ls -A  /data/worknote            # WorkNote 것 외에 다른 게 들어 있지 않은지
> ```
>
> ##### DB 이전 절차 — 앱을 먼저 멈추세요
>
> 실행 중인 DB를 `cp`로 복사하면 안 됩니다. 커밋되지 않은 `-wal` 내용이 빠져 손상된 사본이 됩니다.
>
> ```bash
> # 1) 앱 중지 (필수)
> systemctl stop worknote     # 또는 프로세스 종료
>
> # 2) 전용 디렉토리 준비
> install -d -m 700 -o worknote -g worknote /var/lib/worknote
>
> # 3) 일관된 사본 생성 — .backup은 -wal 내용까지 반영한 사본을 만든다(cp와 다른 점)
> sqlite3 /old/path/worknote.db ".backup '/var/lib/worknote/worknote.db'"
> #   대안: sqlite3 /old/path/worknote.db "VACUUM INTO '/var/lib/worknote/worknote.db'"
>
> # 4) 첨부 디렉토리도 같은 시점 기준으로 이동
> rsync -a /old/path/attachments/ /var/lib/worknote/attachments/
>
> # 5) 절대 경로로 재기동
> WORKNOTE_DB=/var/lib/worknote/worknote.db \
> WORKNOTE_UPLOAD_DIR=/var/lib/worknote/attachments ...
> ```
>
> `.backup`/`VACUUM INTO`는 사본 하나로 정리되므로 `-wal`·`-shm`을 따로 옮길 필요가 없습니다. 파일을 그대로 옮기는 방식을 쓴다면 **앱을 멈춘 뒤** `worknote.db`와 `-wal`·`-shm`을 **함께** 옮기세요. 원본은 새 경로로 기동해 정상 동작을 확인할 때까지 지우지 마세요.
>
> ##### 백업 계정이 그룹 권한으로 접근하고 있었다면
>
> **그 접근은 지금까지 정상적으로 동작하고 있었고, 이 업그레이드에서 끊깁니다.** 이전 버전은 디렉토리 권한을 건드리지 않았으므로, 그룹 읽기로 백업하던 계정은 아무 문제 없이 돌고 있었습니다. `700`으로 조이면 그날부터 **백업이 조용히 실패**합니다(백업 잡이 오류를 삼키면 몇 주 뒤에야 발견됩니다). 재기동 전에 아래 중 하나를 정하세요.
>
> | 방식 | 내용 | 트레이드오프 |
> | --- | --- | --- |
> | **앱 계정으로 백업 실행** (권장) | 백업 잡을 앱 실행 계정의 cron/systemd timer로 옮기거나 `sudo -u worknote sqlite3 ... ".backup ..."`으로 실행 | 저장소는 소유자 전용 유지. 산출물을 백업 계정이 읽을 위치에 두고 **그 위치의 권한·암호화를 따로 통제**해야 합니다 |
> | **산출물만 넘기기** | 앱 계정이 스냅샷을 만들어 교환 디렉토리에 두고, 백업 계정은 거기서만 읽음 | 데이터 저장소 접근을 열지 않음. 교환 디렉토리에 평문 DB가 남으므로 보존 기간·권한을 짧고 좁게 |
> | **`WORKNOTE_STORAGE_STRICT=false`** | 디렉토리를 열어 둔 채 기동. 점검은 WARN으로만 남음 | 그룹이 DB를 계속 읽을 수 있습니다 — 노트 본문·개인정보 전부. 그룹 구성원이 백업 계정 하나뿐인지 확인하고 쓰세요 |
>
> **local 모드는 위 어느 것도 기동을 막지 않습니다.** 기존 디렉토리가 `755`여도 chmod도 경고도 하지 않습니다 — 개인 PC의 프로젝트·홈 폴더가 `755`인 건 정상이고, DB 파일이 `600`이라 내용은 보호됩니다. 앱이 만드는 디렉토리는 `700`, DB 파일은 `600`이 그대로 적용되며, 진짜 오작동(업로드 루트 생성 실패 등)만 경고로 남습니다.
>
> **디렉토리 심볼릭 링크 자체는 실패 사유가 아닙니다** — 별도 볼륨을 링크로 붙인 배치는 그대로 동작합니다. 권한을 바꾸지 않는 대상은 링크를 해석해 검증만 하기 때문입니다. 실패 메시지에는 `(실경로 <target>)`이 함께 표기되니, chmod 전에 그 실경로가 앱 전용인지 확인하세요.

프로세스 실행 계정만 이 디렉토리에 직접 접근하고, 백업은 위 표의 방식 중 하나로 처리하는 것을 권장합니다.

### 업그레이드 시 API 변경 — 공유 링크 열람

`GET /api/share/{token}` 이 **삭제**되고 `POST /api/share/{token}/view` 로 바뀌었습니다. 앱 화면(공유 뷰어)은 함께 갱신되므로 사용자가 할 일은 없지만, **이 엔드포인트를 직접 호출하던 스크립트·사내 연동·모니터링·북마크는 전부 깨집니다.**

| 구분 | 이전 | 현재 |
| --- | --- | --- |
| 열람 | `GET /api/share/{token}` | `POST /api/share/{token}/view` |

- **왜 바뀌었나**: 이 호출은 열람 횟수를 소비하고 감사 로그를 남기는 **상태 변경**입니다. GET으로 두면 외부 사이트가 이미지 태그·링크만으로 남의 공유 링크 열람 횟수를 소진시킬 수 있었습니다.
- **CSRF 검증 대상입니다.** 상태 변경 요청이므로 `Origin`(없으면 `Referer`) 검증을 통과해야 합니다. 브라우저에서 같은 오리진으로 호출하면 자동으로 통과하고, `curl` 등 스크립트에서 호출한다면 `-H "Origin: https://note.domain.co.kr"`처럼 **서비스 오리진을 명시**해야 합니다(프록시 TLS 종단이면 `WORKNOTE_CANONICAL_ORIGIN`과 정확히 같은 값).
- 사용자가 받는 **공유 URL(`.../share.html?token=...`)은 그대로**입니다 — 바뀐 것은 그 화면이 내부적으로 호출하는 API뿐이라, 이미 배포된 공유 링크는 재발급할 필요가 없습니다.
- 인증·권한 규칙은 그대로입니다(로그인 필요, read 권한 불요, 무효 사유는 전부 404 단일).

```diff
  # 스크립트에서 호출하던 곳
- curl -b cookies.txt https://note.domain.co.kr/api/share/$TOKEN
+ curl -b cookies.txt -X POST -H "Origin: https://note.domain.co.kr" \
+      https://note.domain.co.kr/api/share/$TOKEN/view
```

### TLS(HTTPS) 적용

스위치는 `WORKNOTE_TLS_ENABLED=true` 이고, 여기에 자재(키스토어 또는 `server.ssl.bundle`/`server.ssl.certificate`)를 함께 지정합니다. 아무것도 설정하지 않으면 지금까지와 동일하게 HTTP로 뜹니다(설정 변경 불필요).

세션 쿠키 `Secure`는 **직접 설정하지 않습니다.** 실효 TLS 상태 또는 `WORKNOTE_CANONICAL_ORIGIN`이 `https://`인지에서 자동으로 유도됩니다.

> 쿠키 `Secure`를 손으로 켜게 두지 않는 이유: HTTP 배포에서 `Secure`가 켜지면 브라우저가 세션 쿠키를 아예 보내지 않아 **로그인 전면 장애**가 납니다. 반대로 HTTPS인데 안 켜면 평문 유출 창이 남습니다.

#### 모순되는 설정은 기동을 막습니다

조용히 잘못된 상태로 뜨는 것보다 안 뜨는 편이 낫다는 원칙입니다. 아래 조합은 전부 기동 시점에 한국어 조치 문구와 함께 실패합니다.

| 조합 | 조치 |
| --- | --- |
| 키스토어·번들·PEM 지정 + `WORKNOTE_TLS_ENABLED` 미설정 | `WORKNOTE_TLS_ENABLED=true` 설정, 또는 자재 설정 제거 |
| `WORKNOTE_TLS_ENABLED=true` + 자재 전무 | 키스토어(+비밀번호) 또는 번들·PEM 지정 |
| HTTPS로 설정(`WORKNOTE_TLS_ENABLED=true` **또는** 쿠키 `secure=true` 명시) + `WORKNOTE_CANONICAL_ORIGIN`이 `http://…` | canonical-origin을 `https://`로 고치거나, 평문 HTTP 배포라면 HTTPS 설정을 되돌리기. **`SERVER_FORWARD_HEADERS_STRATEGY`를 설정해도 이 실패는 회피되지 않습니다** — 그대로 두면 `403 invalid_origin`으로 전 요청이 막히기 때문입니다 |
| 실효 HTTPS + 쿠키 `secure=false` 오버라이드 | 오버라이드 제거(자동으로 켜집니다) |
| 평문 HTTP + 쿠키 `secure=true` 오버라이드 | `WORKNOTE_CANONICAL_ORIGIN=https://…` 또는 `SERVER_FORWARD_HEADERS_STRATEGY=framework` 설정, 아니면 오버라이드 제거. 단 **`SERVER_FORWARD_HEADERS_STRATEGY`는 canonical-origin이 비어 있거나 `https://`일 때만 유효한 회피책**입니다 — `http://…`면 위 행에 걸려 그대로 실패하므로 canonical-origin을 고쳐야 합니다 |
| `WORKNOTE_CANONICAL_ORIGIN` 형식 불량 | `https://host[:port]` 절대 오리진으로 고치거나 비우기 |

마지막 항목이 중요합니다 — 이전에는 형식이 깨진 값이 **조용히 무시되고** CSRF 기준이 요청에서 유도된 값으로 되돌아갔습니다. 이제는 기동 시점에 걸립니다.

#### 1) 사내 CA에 CSR 제출

```bash
openssl req -newkey rsa:2048 -nodes \
  -keyout worknote.key -out worknote.csr \
  -subj "/CN=note.domain.co.kr/O=회사명" \
  -addext "subjectAltName=DNS:note.domain.co.kr"
```

`worknote.csr`를 사내 CA에 제출해 서버 인증서(`worknote.crt`)와 CA 체인(`ca-chain.crt`)을 받습니다. `subjectAltName`은 필수입니다 — CN만 있는 인증서는 최신 브라우저가 거부합니다. 사용자가 접속할 **모든** 이름(FQDN, 짧은 호스트명 등)을 SAN에 넣으세요.

#### 2) PKCS12로 변환

Java는 PEM(`.crt`/`.key`)을 직접 읽지 않습니다. 키 + 인증서 + 체인을 하나의 PKCS12로 묶습니다.

```bash
openssl pkcs12 -export \
  -inkey worknote.key -in worknote.crt -certfile ca-chain.crt \
  -name worknote \
  -out worknote.p12
# → Enter Export Password: 이 값이 WORKNOTE_TLS_KEYSTORE_PASSWORD

install -m 600 -o worknote -g worknote worknote.p12 /etc/worknote/worknote.p12
shred -u worknote.key   # .p12로 옮긴 뒤 원본 개인키 제거
```

- `-name`의 값이 `WORKNOTE_TLS_KEY_ALIAS`(기본 `worknote`)와 같아야 합니다.
- **개인키(`.key`)와 `.p12`는 소스 저장소·이슈 트래커·채팅 어디에도 올리지 마세요.** 파일 권한 `600`, 앱 실행 계정 소유로 두고 백업은 별도 암호화합니다.

#### 3) 기동

```bash
WORKNOTE_MODE=server \
WORKNOTE_TLS_ENABLED=true \
WORKNOTE_TLS_KEYSTORE=/etc/worknote/worknote.p12 \
WORKNOTE_TLS_KEYSTORE_PASSWORD='키스토어-비밀번호' \
SERVER_PORT=8443 \
WORKNOTE_DB=/data/worknote/worknote.db \
WORKNOTE_UPLOAD_DIR=/data/worknote/attachments \
WORKNOTE_2FA_KEY=... \
java -jar worknote-0.1.0.jar
```

- 포트는 기본 8080 그대로입니다. HTTPS 관례 포트로 바꾸려면 `SERVER_PORT`를 지정하세요(1024 미만 포트는 root 권한이나 `setcap`이 필요합니다).
- **HTTP·HTTPS 동시 오픈은 지원하지 않습니다**(단일 포트). 평문 접속을 리다이렉트하려면 앞단에 프록시를 두세요.
- 확인: `curl -v --cacert ca-chain.crt https://note.domain.co.kr:8443/api/health`

#### 리버스 프록시가 TLS를 종단하는 경우 — 반드시 읽으세요

프록시가 HTTPS를 받고 앱에는 평문 HTTP로 넘기는 구성이라면 `WORKNOTE_TLS_ENABLED`를 켜지 않습니다. 대신 아래 설정이 **필수**입니다. 빠뜨리면 **로그인을 포함한 모든 상태 변경 요청이 403 `invalid_origin`으로 막혀 앱이 통째로 멈춥니다.**

이유: CSRF 방어가 브라우저의 `Origin` 헤더를 서버가 인식한 자기 오리진과 비교하는데, 프록시 뒤에서는 서버가 보는 스킴이 `http`, 브라우저가 보낸 Origin은 `https://...`라 **항상 불일치**합니다.

```bash
# 권장 — 비교 기준을 요청이 아니라 고정값으로
WORKNOTE_CANONICAL_ORIGIN=https://note.domain.co.kr
```

이 값이 `https://`로 시작하면 세션 쿠키 `Secure`도 함께 켜집니다(앱 자체는 HTTP로 떠 있어도 브라우저 구간은 HTTPS이므로 켜는 게 맞습니다). 값은 사용자가 브라우저 주소창에 치는 오리진과 **정확히** 같아야 합니다(스킴·호스트·비표준 포트까지).

```bash
# 대안/병용 — 프록시가 보내는 X-Forwarded-Proto/Host를 신뢰
SERVER_FORWARD_HEADERS_STRATEGY=framework
```

이 필터는 인증 필터보다 먼저 실행되므로 요청 스킴 자체가 `https`로 교정되어 Origin 검증도 통과합니다. 단, **프록시가 클라이언트가 보낸 `X-Forwarded-*`를 지우고 자기 값으로 덮어쓸 때만** 사용하세요(그렇지 않으면 헤더 위조로 검증이 무력화됩니다). 리다이렉트·절대 URL 생성까지 바로잡히므로, `WORKNOTE_CANONICAL_ORIGIN`과 **함께** 쓰는 것을 권장합니다.

nginx 예시:

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;   # 클라이언트 값을 덮어씀
    proxy_set_header X-Forwarded-Host  $host;
    client_max_body_size 64m;                     # 멀티파트 상한과 맞춤
}
```

#### 갱신

무중단 갱신은 지원하지 않습니다(재기동 수 초 소요). 만료 **전에** 미리 준비하세요.

1. 만료일 확인: `openssl pkcs12 -in /etc/worknote/worknote.p12 -nokeys -passin pass:... | openssl x509 -noout -enddate`
2. 새 키·CSR 생성 → 사내 CA 재발급 (키 재사용보다 **키 교체 권장**)
3. 위 2)를 반복해 새 `.p12` 생성, 기존 파일을 백업 후 교체
4. 프로세스 재기동 → `curl`로 새 만료일 확인
5. CA 체인 자체가 갱신되면 `-certfile`에 새 체인을 넣어 다시 만들어야 합니다

만료된 인증서로는 기동은 되지만 브라우저가 전부 경고·차단합니다. 만료 30일 전 알림을 운영 캘린더에 등록해 두세요.

## 3. 최초 설정 체크리스트

1. `WORKNOTE_2FA_KEY` 생성·보관 후 server 모드 기동
2. `admin`으로 로그인 → **즉시 2FA 등록** (admin은 유예 기간(기본 7일) 후 미등록 시 기능이 차단됨)
3. 관리자 콘솔 → **팀·스페이스**: 팀 생성, 최상위 폴더를 팀 스페이스로 지정
4. **역할 관리**: 필요 시 커스텀 역할 생성 (시스템 역할 3종은 수정 불가)
5. **업로드 정책**: 허용 확장자·용량 확인 (기본: png,jpg,jpeg,gif,webp,pdf,docx,xlsx,pptx,txt,md,csv,zip / 25MB)
6. (선택) SMTP 설정 — 2FA 복구 코드 메일 발송에 필요. 사내 SMTP가 STARTTLS를 지원하면 `WORKNOTE_SMTP_STARTTLS=true`로 평문 전송을 차단하세요(복구 코드가 메일 본문에 실림).
7. (선택) **Redmine 연동** 설정 — base URL은 `http`/`https`만, loopback·link-local·0.0.0.0 등 특수 대역은 거부됩니다(SSRF 방어). 사내망 사설 IP는 허용됩니다.
8. 백업 스케줄 구성 ([§13](#13-백업과-복구))

> **보안 배포 체크리스트**: [TLS 적용](#tlshttps-적용)(프록시 종단이면 `WORKNOTE_CANONICAL_ORIGIN` 필수), `WORKNOTE_DB`를 전용 디렉토리의 **절대 경로**로 지정(server 모드 필수 — [데이터 파일 권한](#데이터-파일-권한)), 필수 시크릿(`WORKNOTE_ADMIN_PASSWORD`·`WORKNOTE_2FA_KEY`·`WORKNOTE_SMTP_*`·`WORKNOTE_TLS_KEYSTORE_PASSWORD`) env 주입 확인. 상세는 [보안 조치 결과](security/2026-07-03-remediation.md) 참조.

## 4. 사용자 관리

### 계정 수명주기

```
가입 신청(pending) ──관리자 승인──> active ──비활성화──> disabled
        └── 반려(비활성화 처리)          └── 재활성화 가능
```

- **가입 승인**: 관리자 콘솔 → 가입 승인 대기. 승인 시 기본 역할 **방문자**(읽기 전용)로 활성화됩니다. 승인 후 필요한 역할로 변경하세요.
- **직접 생성**: 사용자 관리 → 계정 추가(사번·이름·이메일·역할·초기 비밀번호).
- **비밀번호 초기화**: 사용자 관리에서 새 비밀번호 지정(10자 이상). 해당 사용자의 **다른 세션은 즉시 무효화**됩니다.
- **2FA 초기화**: 기기 분실 등으로 복구 메일도 못 받는 사용자용. 시드가 삭제되고 유예 기간이 다시 부여됩니다.
- **비활성화**: 로그인이 즉시 차단됩니다. 데이터는 유지됩니다.
- 실패한 로그인·2FA·복구 시도는 감사 로그에 기록되며, **계정 5회·같은 IP 30회 연속 실패 시 5분간 자동 잠금**됩니다(잠금 응답 HTTP 429). 잠금 전이는 감사 로그 `auth.lockout`, 잠금 중 시도는 `login.locked`/`2fa.locked`/`recover.locked`로 남습니다. 잠금은 인메모리라 서버 재기동 시 초기화됩니다. 실패 자체(`login.fail`)도 주기적으로 확인하세요.

### 아무도 로그인할 수 없을 때 — 최후 복구(break-glass)

위 조치는 전부 **로그인 가능한 관리자가 한 명은 있어야** 합니다. 그 전제가 깨지는 경우가 있습니다.

> 유일한 관리자가 2FA를 켠 뒤 휴대폰을 분실했고, `WORKNOTE_SMTP_HOST`가 설정돼 있지 않아 복구 메일도 받을 수 없다.

아무도 로그인할 수 없으므로 아무도 초기화해 줄 수 없습니다. 이때를 위한 경로가 **센티넬 파일**입니다.

이 경로를 쓸 수 있는 사람은 **앱 실행 계정(예: `worknote`), 또는 데이터 디렉토리에 파일을 만들 수 있는 사람**입니다. 호스트에 셸로 들어갈 수 있다는 것만으로는 부족합니다 — 데이터 디렉토리는 `700`·앱 소유이므로, 그 계정이 되거나(`sudo -u worknote` 또는 root) 데이터 디렉토리에 직접 쓸 수 있어야 합니다.

**데이터 디렉토리가 놓인 위치도 조건입니다.** 아래 예시의 `/data/worknote`처럼, 그 **위 경로**(`/data`, `/`)는 `root` 또는 앱 실행 계정 소유여야 하고 그룹·타인 쓰기가 열려 있으면 안 됩니다. `/var/lib/worknote`·root 소유 `/data` 같은 표준 배치는 그대로 통과하지만, **배포 전용 계정이 `/data`를 소유하거나 `/home/누군가/...` 아래에 둔 배치는 센티넬을 놓았을 때 기동이 거부됩니다** — 이유와 조치는 아래 "앱이 파일의 출처를 검사합니다" 절에 있습니다. 평상시(센티넬이 없을 때) 기동에는 영향이 없습니다.

```bash
# 1) 서비스 중지
systemctl stop worknote

# 2) DB 파일 옆에 센티넬 생성 (파일명 고정: break-glass)
#    반드시 앱 실행 계정으로, 600으로 만드세요 — 앱이 소유자·권한을 검사하고 통과하지 못하면 기동을 거부합니다.
sudo -u worknote install -m 600 /dev/null /data/worknote/break-glass
sudo -u worknote tee /data/worknote/break-glass >/dev/null <<'EOF'
emp=admin
password=새로운-비밀번호-10~128자
EOF

# 3) 기동 — 부팅 과정에서 소비되고 파일이 삭제됩니다
systemctl start worknote
```

> **평문 비밀번호를 명령줄에 넣는 것의 대가.** 위 `heredoc`에 적은 비밀번호는 파일이 지워진 뒤에도 **셸 히스토리(`~/.bash_history`)·터미널 스크롤백·세션 감사(`script`, 터미널 녹화, 원격 접속 로깅)** 에 남을 수 있습니다. 앱은 이 값을 로그·감사에 남기지 않지만, 그 앞단은 앱이 통제할 수 없습니다.
>
> - **가장 안전한 방법은 `password` 줄을 아예 쓰지 않는 것입니다.** 기존 비밀번호를 기억하고 있다면 2FA만 풀고(아래) 로그인한 뒤 화면에서 바꾸세요 — 평문이 어디에도 만들어지지 않습니다.
> - 꼭 재설정해야 한다면 히스토리에 남지 않는 방법을 쓰세요: 편집기로 직접 입력(`sudo -u worknote install -m 600 /dev/null /data/worknote/break-glass && sudo -u worknote vi /data/worknote/break-glass`)하거나, 셸이 `HISTCONTROL=ignorespace`면 명령 앞에 공백을 붙입니다.
> - 어느 쪽이든 **복구 후 그 비밀번호를 즉시 변경**하고, 남아 있을 수 있는 히스토리를 정리하세요.

- `emp`는 **필수**, `password`는 **선택**(10~128자)입니다. `password` 줄을 지우면 2FA만 풀고 비밀번호는 그대로 둡니다(비밀번호는 기억하는데 기기만 잃은 경우 — 위 경고대로 이쪽이 더 안전합니다).
- 수행 내용: **2FA 시드 폐기 + 미사용 복구코드 무효화 + 2FA 유예 재시작**, (지정 시) 비밀번호 재설정 + 기존 세션 무효화, 비활성/승인대기 계정이면 `active`로 복구. 다음 로그인을 막는 요소를 한 번에 걷어냅니다.
- 감사 로그에 `who=break-glass`, `act=auth.break_glass`, `target=<사번>`으로 남고 서버 로그에 WARN이 찍힙니다. **비밀번호는 로그에 남지 않습니다.**
- 복구 후 관리자는 2FA 유예 기간 안에 **재등록**해야 합니다.

**앱이 파일의 출처를 검사합니다.** 아래를 하나라도 만족하지 못하면 **기동을 거부**하고 아무 작업도 하지 않습니다.

| 조건 | 이유 |
| --- | --- |
| 일반 파일이고 **심볼릭 링크가 아님** | 링크를 따라가면 검사한 대상과 읽는 대상이 달라집니다 |
| 파일 소유자 = **앱 실행 계정** | 남이 놓아둔 파일로 계정이 넘어가면 안 됩니다 |
| 파일이 **그룹·타인에게 닫힘**(`600`) | 이 파일엔 평문 비밀번호가 들어갑니다 |
| 상위 디렉토리 소유자 = 앱 실행 계정, **`700`** | 그룹·타인에게 **쓰기**가 열려 있었다면(`775`·`777` 등) 누구나 이 자리에 파일을 놓을 수 있었다는 뜻입니다. 판정은 그보다 엄격해서 읽기만 열린 `755`도 거부합니다 — `700`이 값싸고 확실한 선이기 때문입니다 |
| **경로 해석이 지나가는 모든 디렉토리의 소유자 = 앱 실행 계정 또는 `root`** | 쓰기 비트가 없어도 **디렉토리 소유자**는 자기 디렉토리의 엔트리를 언제든 rename할 수 있습니다(원하면 먼저 자기 디렉토리를 chmod하면 그만입니다). 즉 `/home/other/worknote/data`가 `700`·앱 소유여도 `other`가 `worknote`를 소유하면 데이터 디렉토리를 통째로 바꿔치기할 수 있습니다 |
| **그 디렉토리들이 그룹·타인에게 쓰기 가능하지 않음** | 부모가 `700`이어도 그 위에 쓸 수 있는 사람은 **데이터 디렉토리를 통째로 자기 것으로 바꿔치기**할 수 있습니다(디렉토리 엔트리 rename). 자식의 `700`은 그걸 막지 못하므로, 부모만 봐서는 아래 "왜 백도어가 아닌가"의 근거가 성립하지 않습니다 |
| **DB 경로가 `..`로 끝나지 않음**(`/a/b/../worknote.db` 형태가 아님) | 그 형태에서만 조상 검사와 부모 확인이 서로 다른 관측이 되어 그 사이의 디렉토리 교체를 탐지할 수 없습니다. 경로 **중간**의 `..`와 심링크는 그대로 지원합니다 — 아래 "센티넬 경로" 항목에 조치가 있습니다 |
| 4KB 이하 | 센티넬은 두 줄입니다 |

조상 검사는 **커널이 실제로 지나가는 디렉토리 전부**를 봅니다 — 데이터 디렉토리를 심링크로 붙인 배치라면 링크가 놓인 디렉토리도, 링크 타깃의 조상도, **중간 심링크 타깃의 조상까지** 포함합니다. 각 디렉토리에서 보는 것은 **소유자**(앱 실행 계정 또는 `root`)와 **그룹·타인 쓰기 비트** 둘입니다. `/`, `/var`, `/var/lib`, `/srv`, root 소유 `/data`가 `755`인 것은 정상이고 문제가 되지 않습니다.

**`/tmp`처럼 sticky가 붙은 디렉토리(`1777`)는 조건부로 허용**합니다. sticky는 "누구도 rename하지 못한다"가 아니라 "**엔트리 소유자·디렉토리 소유자·특권 사용자만** rename한다"이므로, 그 디렉토리가 앱 계정·root 소유이고 **그 안에서 지나가는 엔트리도 앱 계정(또는 root) 소유**일 때만 인정합니다. `/tmp` 아래에 앱 소유 디렉토리를 두는 정상 배치는 그대로 통과하고, 남이 만든 심링크를 지나가는 배치는 걸립니다.

**거부 메시지를 조치할 때**: 메시지는 문제의 경로(**실경로** — 심링크를 지난 뒤의 실제 디렉토리)와 현재 소유자·권한을 지목합니다.

- 그 디렉토리가 **WorkNote 전용**이라면 메시지대로 `chmod g-w,o-w <경로>`를 실행하고 재기동하세요.
- **다른 서비스·배포 계정과 공유하는 디렉토리라면 권한을 조이지 마세요.** `/data`처럼 의도적으로 `775`인 조상에 `chmod g-w,o-w`를 하면 다른 서비스나 배포가 깨집니다. 그때는 **데이터 디렉토리를 안전한 경로로 이전**하는 것이 답입니다(예: `/var/lib/worknote` — 조상이 전부 `root` 소유 `755`). 소유자 규칙에 걸린 경우(`/home/other/...` 아래 등)도 마찬가지로 `chown`이 아니라 **이전**이 정답입니다.
- 즉 **배포 전용 계정이 조상 디렉토리를 소유하는 배치는 센티넬을 놓았을 때 기동이 거부됩니다.** 의도된 fail-closed입니다 — 그 계정을 쥔 사람은 앱 계정이 아니면서도 데이터 디렉토리를 갈아치울 수 있고, 그러면 이 기능의 전제가 성립하지 않습니다. 평상시(센티넬이 없을 때) 기동에는 영향이 없습니다.

**`root` 판정은 이름으로 합니다 — 안전한 쪽으로 틀릴 수 있습니다.** 앱에는 uid를 숫자로 읽는 방법이 없어 조상 소유자가 `"root"`라는 **이름**으로 보이는지를 봅니다. `/etc/passwd`가 없는 최소 컨테이너나 LDAP·NFS의 id 매핑이 어긋난 마운트에서는 uid 0이 `root`로 해석되지 않고 숫자(`0`) 그대로 보일 수 있고, 그러면 **정상적인 root 소유 조상이 거부되어 기동이 멈춥니다.** 반대 방향(남의 디렉토리를 통과시키는 쪽)으로는 틀리지 않습니다. 이 경우 `chown`으로 우회하려 하지 말고 **데이터 디렉토리를 앱 실행 계정 소유의 조상 아래로 옮기세요**(예: 앱 계정이 소유한 `/var/lib/worknote` 아래) — 앱 계정 쪽 비교는 이름 해석 경로가 같아서 둘 다 숫자로 보여도 서로 맞습니다. 컨테이너라면 `/etc/passwd`에 해당 uid 항목을 넣어 주는 것도 방법입니다.

이 검사는 `WORKNOTE_STORAGE_STRICT=false`로 저장소 점검을 꺼 두었더라도 **그대로 적용됩니다.** 그 스위치는 저장소 하드닝 경고에 대한 결정이지, 복구 경로를 넓히는 스위치가 아닙니다. POSIX 권한이 없는 파일시스템(Windows 등)에서는 이 전제를 확인할 방법이 없으므로 **기능 자체가 비활성**입니다.

**중단된 복구**: 처리 직전에 센티넬은 `break-glass.processing`으로 이름이 바뀌고(선점), 트랜잭션 커밋 뒤에 삭제됩니다. 기동 시 이 `.processing` 파일이 남아 있으면 이전 시도가 중간에 끊긴 것이므로 **기동이 실패합니다** — 적용됐는지 아닌지 앱이 알 수 없기 때문입니다. **이때 다시 실행되는 일은 없습니다**(재적용이 아니라 중단입니다). 남은 파일은 증거이므로 앱이 지우지 않습니다.

서비스가 뜨지 않는 상태이므로 화면으로는 확인할 수 없습니다. **DB를 직접 열어 판단하세요.** 계정 수술과 감사 기록은 **같은 트랜잭션**이므로 "이번 시도가 커밋됐는가"는 DB에 남습니다.

> **감사 행이 있다는 것만으로는 판별할 수 없습니다.** 과거에 같은 계정으로 성공한 브레이크글래스가 있으면 그 행이 **이미** 있기 때문입니다. `.processing` 파일에도 감사 행에도 시도를 잇는 식별자가 없으므로, **남은 파일의 수정 시각(mtime)을 기준선으로 삼아 시각을 비교**해야 합니다.

> **먼저 시간대를 맞추세요 — 여기서 어긋나면 판정이 통째로 뒤집힙니다.** 감사 로그의 `at`과 `totp_grace_start`는 **JVM 기본 시간대의 시각**이 오프셋 없이(`2026-08-27T13:31:02`) 저장됩니다. 반면 `stat`이 찍는 시각은 **명령을 실행한 셸의 시간대**입니다. 서비스가 `TZ=UTC`로 뜨고 운영자 셸이 KST면 두 값이 9시간 어긋나 **적용된 것을 미적용으로, 미적용을 적용으로** 읽게 됩니다. 미적용을 적용으로 오판하면 증거(`.processing`)를 지우고 다시 잠깁니다.

```bash
# 0) JVM 시간대 확인 — 서버 로그의 타임스탬프에는 오프셋이 붙어 나옵니다. 그 오프셋이 JVM의 시간대입니다.
journalctl -u worknote -n 3 --no-pager -o cat   # 예: 2026-08-27T04:31:05.412+00:00 ERROR ... → JVM은 UTC
date '+%Y-%m-%d %H:%M:%S %z'                    # 예: 2026-08-27 13:31:40 +0900   → 셸은 KST (9시간 차)

# 1) 기준선 — 남은 .processing 파일이 마지막으로 쓰인 시각(rename은 mtime을 바꾸지 않습니다)
#    데이터 디렉토리가 700이므로 앱 계정이나 root로 실행하세요.
#    0)에서 시간대가 갈렸다면 JVM 시간대로 맞춰 찍으세요 — 아래는 JVM이 UTC일 때의 예입니다.
sudo -u worknote stat -c '%y' /data/worknote/break-glass.processing        # 셸 시간대
sudo -u worknote env TZ=UTC stat -c '%y' /data/worknote/break-glass.processing   # JVM 시간대로 환산

# 2) 조회는 '일회용 복사본'에서 합니다 — 원본은 증거이므로 손대지 않습니다.
#    원본을 sqlite3 -readonly 로 열지 마세요: 끊긴 트랜잭션의 핫 저널(worknote.db-journal)이 남아 있으면
#    SQLite는 읽기 전에 롤백부터 해야 하는데 롤백은 쓰기라서 SQLITE_READONLY_ROLLBACK 으로 실패합니다.
#    본체와 보조 파일(-journal, 설정을 바꿨다면 -wal·-shm)을 반드시 '함께' 복사하세요(이유는 아래 주의).
#    기동에 실패한 상태라 앱이 DB를 잡고 있지 않으므로 이 복사본은 일관된 스냅샷입니다.
sudo -u worknote install -d -m 700 /tmp/bg-check
sudo -u worknote sh -c 'cp -p /data/worknote/worknote.db* /tmp/bg-check/'

# 3) 그 시각 이후의 흔적이 있는가 (복사본은 쓰기 가능하게 엽니다 — 필요하면 SQLite가 여기서 롤백합니다)
sudo -u worknote sqlite3 /tmp/bg-check/worknote.db \
  "SELECT at, who, act, target FROM audit_log WHERE act='auth.break_glass' ORDER BY at DESC LIMIT 5;"

# 4) 계정 상태도 함께 (2FA 등록 여부 / 계정 상태 / 유예 시작 시각)
sudo -u worknote sqlite3 /tmp/bg-check/worknote.db \
  "SELECT u.emp, u.status, u.totp_grace_start, t.enabled
     FROM app_user u LEFT JOIN user_totp t ON t.user_id = u.id WHERE u.emp='admin';"

# 5) 복사본에는 비밀번호 해시·세션이 들어 있습니다 — 확인이 끝나면 지우세요.
sudo -u worknote rm -rf /tmp/bg-check
```

- 가장 최근 감사 행의 `at`과 그 계정의 `totp_grace_start`가 **둘 다 mtime 이후** = 이번 시도가 **커밋됐습니다**(2FA 해제·유예 재시작·지정했다면 비밀번호까지). `.processing`을 지우고 기동한 뒤 로그인하세요.
- **둘 다 mtime 이전**(또는 아예 없음) = 이번 시도는 **아무것도 적용하지 않았습니다**(트랜잭션 통째 롤백). `.processing`을 지우고 센티넬을 다시 만들어 기동하세요.
- **왜 이 비교가 성립하나**: 센티넬은 소비될 때 지워지므로 지금 남아 있는 파일은 **이번 시도를 위해 새로 만든 것**입니다. 따라서 과거 복구의 흔적은 반드시 mtime보다 앞에 오고, 이번 시도의 흔적은 반드시 뒤에 옵니다. **단, 두 값을 같은 시간대로 놓고 비교했을 때만** 그렇습니다(위 0단계).
- **둘이 엇갈리거나 판단이 서지 않으면**(예: 파일을 `cp -p`·`touch -t`로 만들어 mtime이 과거이거나, 그 사이 서버 시계를 조정했거나, **JVM 시간대를 확인할 수 없다면**) **적용되지 않은 것으로 보고 재시도하세요.** 앱이 뜨지 못한 동안에는 아무도 로그인해 2FA를 재등록하거나 비밀번호를 바꿀 수 없었으므로, 다시 적용해도 **되돌아갈 상태가 없습니다.** 앱이 스스로 재시도하지 않는 이유는 앱이 이 사실을 알 수 없기 때문입니다 — 운영자는 알 수 있습니다.

> **원본을 열지 말고, 다른 계정으로도 열지 마세요.** root로 열면 저널/보조 파일이 root 소유로 생겨 앱이 못 쓰게 됩니다. 원본을 `sqlite3 -readonly`로 여는 것도 답이 아닙니다 — 끊긴 트랜잭션의 **핫 저널**(`worknote.db-journal`)이 남아 있으면 SQLite는 읽기 전에 그것을 **롤백**해야 하고, 롤백은 쓰기라서 읽기 전용 연결은 `SQLITE_READONLY_ROLLBACK`으로 **실패합니다.** 그래서 위 절차는 본체와 보조 파일을 **일회용 복사본**으로 함께 옮긴 뒤 그 복사본을 쓰기 가능하게 엽니다(롤백은 복사본에서 일어나고 원본은 증거로 남습니다). `sqlite3`가 없는 폐쇄망이라면 같은 복사본을 조회 가능한 장비로 가져가 확인하세요 — 이때도 `worknote.db-journal`(설정을 바꿨다면 `-wal`·`-shm`)이 있으면 **반드시 함께** 가져가야 합니다.
>
> 왜 함께 복사해야 하는지는 모드에 따라 다릅니다. 이 앱의 기본인 rollback journal(`journal_mode=delete`)에서 **커밋된 데이터는 본체(`worknote.db`)에 있고**, `worknote.db-journal`은 **끊긴 트랜잭션을 커밋 전 상태로 되돌리기 위한 원본 페이지**입니다(정상 종료 후에는 아예 없습니다 — 남아 있다면 트랜잭션이 중간에 끊겼다는 뜻입니다). 저널을 빼고 본체만 복사하면 SQLite가 되돌릴 자료를 잃어 **롤백됐어야 할 미완료 트랜잭션의 페이지가 섞인 상태**를 보게 되고, 그러면 적용되지 않은 것을 적용된 것으로 오판할 수 있습니다. WAL(`-wal`)로 바꾼 배치라면 반대로 **최근 커밋이 `-wal` 쪽에** 있으므로 그것을 빼면 커밋이 빠집니다. 어느 쪽이든 조치는 같습니다 — **중지한 뒤 본체와 보조 파일을 함께** 가져가세요.

**형식 규칙**: Java properties 형식이라 값 안의 `\`는 이스케이프입니다(`\\`로 쓰세요). `emp`/`password` 외의 키가 있으면 기동이 실패합니다 — `pasword=`처럼 오타를 내면 바뀐 줄 알고 다시 잠긴 문 앞에 서게 되므로 조용히 넘기지 않습니다.

**문제가 있으면 기동이 실패하고 파일은 남습니다** (고쳐서 다시 띄우세요): 사번이 없음 · 비밀번호가 10자 미만 · `password=`가 빈 값 · 알 수 없는 키 · 파일을 읽을 수 없음. **성공 후 파일 삭제에 실패해도 기동이 실패합니다** — 그 시점에 남아 있는 것은 `break-glass.processing`이고, 그 파일이 남은 채로 재기동하면 위의 "중단된 복구"로 걸려 **어차피 기동이 멈춥니다.** 그 정지가 아무 설명 없이 찾아오게 두느니, 이미 복구가 적용됐다는 사실과 지워야 할 파일 경로를 알려주면서 지금 멈추는 편이 낫습니다.

> #### 왜 이게 백도어가 아닌가
>
> 트리거가 **DB 부모 디렉토리(`700`, 앱 계정 소유)에 파일을 만들 수 있는 능력**이기 때문입니다. 거기에 파일을 만들 수 있는 사람은 이미 `worknote.db`를 직접 열어 고칠 수 있으므로, 이 기능으로 **새로 생기는 권한이 없습니다.** 손으로 SQL을 치던 복구를 원자적이고 감사되는 한 번으로 바꾼 것뿐입니다.
>
> 이 논거는 **주장이 아니라 검사**입니다(위 조건 표). 부모의 `700`만으로는 부족해서 **경로 해석이 지나가는 디렉토리 전부**를 봅니다 — 그중 하나라도 제3자가 소유하거나 그룹·타인 쓰기 가능하면 데이터 디렉토리를 통째로 바꿔치기해 "700 앱 소유 디렉토리"인 척 만들 수 있고, 그러면 DB를 읽지도 못하던 사람이 관리자 비밀번호를 지정하게 되기 때문입니다. 전제를 확인할 수 없으면 실행하지 않고 **기동을 세웁니다.**
>
> 검증·읽기·선점(`.processing` rename)·정리는 **한 번 연 디렉토리 핸들** 위에서 수행합니다 — 각각 경로로 다시 해석하면 그 사이에 파일이나 디렉토리가 갈아끼워져 "검사한 것과 다른 파일을 실행"할 수 있기 때문입니다. 실제로 보장되는 것과 아닌 것을 정확히 적으면 이렇습니다.
>
> | 무엇을 | 어떻게 |
> | --- | --- |
> | **부모 디렉토리 고정** | 열어 둔 디렉토리 핸들 자체가 그 디렉토리입니다. 이후 경로 상의 엔트리가 다른 디렉토리로 갈아끼워져도 읽고·옮기고·지우는 곳은 열어 둔 그 디렉토리입니다(리눅스) |
> | **조상 체인·소유자·권한 조건** | 위 조건 표 그대로 강제됩니다. 조상과 부모의 사실은 **한 번의 경로 해석**에서 함께 얻습니다 |
> | **파일 교체** | 막지 못하고 **탐지해서 거부**합니다. 열린 디렉토리 핸들도 그 안의 *이름*은 매번 다시 조회하므로, 검증 시점의 파일 식별자(dev+ino)를 기억해 **읽은 직후·rename 직전에 다시 확인**하고 어긋나면 기동을 세웁니다. 탐지되는 것은 정확히 **두 관측 시점의 파일 식별자 불일치**이며, 그 이상은 아닙니다 — 아래 세 줄이 그 바깥입니다 |
> | **읽는 도중의 교체** | **탐지하지 못합니다.** 열린 스트림에서 파일 식별자를 얻는 표준 API가 없어 창을 좁힐 수 있을 뿐 닫을 수 없습니다 |
> | **확인 → rename 사이의 교체** | **탐지하지 못합니다.** 확인 직후 같은 이름에 다른 파일이 놓이면 `.processing`으로 옮겨지는 것은 **그 파일**입니다. 복구는 이미 읽어 둔 원래 내용으로 커밋되고 지워지는 것은 놓인 쪽이라, 원래 센티넬이 남아 **다음 기동에 다시 적용**될 수 있습니다(rename 자체는 원자적이지만 "확인한 그 파일을 옮긴다"까지 원자적이지는 않습니다) |
> | **파일 식별자 재사용(ABA)** | **탐지하지 못합니다.** 식별자(dev+ino)의 유일성은 **정적 파일시스템**에서만 보장되고, 삭제된 식별자를 재사용하는지는 파일시스템 구현에 달렸습니다 — 지운 자리에 만든 파일에 같은 식별자가 나오면 위 재확인은 전부 통과합니다(ext4에서 흔한 형태입니다) |
>
> 위 세 줄의 창을 **실제로 쓰려면 `700`·앱 소유 디렉토리에 쓸 수 있어야 합니다.** 그 능력이 있으면 이미 `worknote.db`를 직접 열어 고칠 수 있으므로, 이 한계들로 **새로 생기는 권한은 없습니다** — 이 절 첫 문단의 논거와 같은 문장입니다. 재확인의 값어치는 "권한 없는 교체를 막는 것"이 아니라 **검증하지 않은 파일을 조용히 실행하지 않는 것**에 있습니다.
>
> 디렉토리 고정은 JDK가 `SecureDirectoryStream`을 제공하는 플랫폼(**리눅스 배포**)에서 적용됩니다. macOS 등 제공하지 않는 플랫폼에서는 **경로 기반으로 동작하며, 위 조건 검사도 파일 식별자 재확인도 완전히 동일하고** 없는 것은 디렉토리 고정뿐입니다(= 시간차 창이 넓습니다). 운영 배포가 리눅스라면 이 차이는 해당되지 않습니다.
>
> 그래서 **HTTP 엔드포인트가 없습니다.** API도, 관리자 콘솔 버튼도, 원격에서 닿는 경로도 일절 없습니다 — 하나라도 네트워크로 노출되는 순간 위 논거가 무너집니다. 이 성질은 유지되어야 하며, 원격 트리거를 추가해 달라는 요구는 거절하세요.
>
> local 모드(무인증)에서는 되살릴 로그인이 없으므로 아무 작업도 하지 않고 파일만 삭제합니다(평문 비밀번호가 남아 나중에 server 모드로 전환할 때 발동하는 것을 막기 위해서입니다).

**센티넬 경로를 바꾸는 설정은 일부러 두지 않았습니다.** 위치는 항상 `<DB 부모>/break-glass` 한 곳입니다 — 경로를 설정으로 열면 공용 디렉토리를 가리키는 오설정 한 번으로 위 전제가 통째로 깨지고, 그것을 막아 주는 것은 아무것도 없기 때문입니다. 여기서 "DB 부모"는 `WORKNOTE_DB` 문자열을 자른 결과가 아니라 **OS가 실제로 여는 DB 파일이 놓인 디렉토리**입니다 — 경로가 심링크를 지나가더라도, `..`가 경로 **중간**에 있더라도(`/a/b/../c/worknote.db`) `ls -l`로 보이는 그 DB 옆에 만들면 됩니다.

**다만 DB 경로가 `..`로 끝나면**(`/a/b/../worknote.db`처럼 DB 파일 **바로 앞** 컴포넌트가 `..`이면) **센티넬을 놓았을 때 기동이 거부됩니다.** 그 형태에서만 조상 검사와 부모 확인이 **서로 다른 관측**이 되어(`..`는 디렉토리로 들어가는 단계가 아니라 거슬러 올라가는 단계라 부모의 상태가 그 순회에 남지 않습니다) 그 사이의 디렉토리 교체를 탐지할 수 없고, 표준 API로 그 창을 닫을 방법이 없기 때문입니다. 조치는 간단합니다 — `readlink -f`로 앱이 실제로 여는 DB 파일의 경로를 확인해 그 경로를 `WORKNOTE_DB`에 적고, 센티넬을 그 DB 옆에 놓은 뒤 재기동하세요. **평상시(센티넬이 없을 때) 기동에는 영향이 없습니다.**

## 5. 권한 모델

> 원본 설계: [권한·디렉토리 설계 스펙](superpowers/specs/2026-06-10-worknote-권한-디렉토리-design.md)

**유효 권한 = 역할 상한(무엇을 할 수 있는가) ∩ ACL 범위(어느 리소스에서인가)**

### 역할 — 능력의 상한

| 역할 | 종류 | 능력(caps) |
| --- | --- | --- |
| 관리자(admin) | 시스템 | 모든 관리 + 리소스 능력 |
| 일반사용자(operator) | 시스템 | `res.read/edit/create/delete/export/share` |
| 방문자(visitor) | 시스템 | `res.read` |
| (커스텀) | 사용자 정의 | 아래 11종 조합 |

능력 11종 — 관리: `admin.users` `admin.permissions` `admin.roles` `admin.security` `admin.audit` / 리소스: `res.read` `res.edit` `res.create` `res.delete` `res.export` `res.share`

시스템 역할은 수정·삭제할 수 없습니다(콘솔에서 보기 전용). 역할이 없는 능력은 ACL로 아무리 허용해도 발휘되지 않습니다.

### ACL — 리소스의 범위

- 주체: 개인 / 팀 / 전체(`@all`), 종류: `read` / `edit` / `deny`
- **폴더에서 하위로 상속**되며, 노드 단위 deny로 구멍(카브아웃)을 냅니다.
- **deny 절대 우선**: 개인 grant로도 팀 deny를 뚫을 수 없습니다.
- **deny-sticky**: 조상에서 deny된 주체는 더 가까운 하위 allow로도 되살아나지 않습니다(deny 아래 재허용 없음).
- 다중 주체(개인+소속 팀들) 해석은 deny-우선 합집합입니다.

### 팀과 스페이스

- 팀은 **그룹**입니다(역할이 아님). 팀에 사용자를 넣고, ACL 주체로 팀을 지정합니다.
- 최상위 폴더를 **팀 스페이스**로 지정하면 소유 팀에 자동 grant됩니다. 스페이스 간 이동은 강한 노출 경고 대상입니다.

### 공개(public)

- 폴더에 public을 지정하면 하위로 캐스케이드되고, 노트 단위로 제외(exclude)할 수 있습니다. 새 노트는 기본 제외입니다.

### 이름·이동·권한의 관계

트리는 안정적 id 기반이라 **이름 변경은 권한에 무영향**, **이동은 위치의 상속을 따라감**입니다. 이동으로 열람 가능 집합이 바뀌면 사용자에게 사전 경고(move-preview)가 뜨고 감사에 남습니다.

## 7. 공유 링크 관리

- 공유 링크는 **deny를 넘는 유일한 read 예외**입니다. 그 대신 만료(1~365일)·취소·열람 수 제한·대상 지정(사번 목록)이 있고 생성/열람/취소가 전부 감사 기록됩니다.
- **로그인은 여전히 필요합니다** — 링크는 권한의 예외이지 인증의 예외가 아닙니다. 비로그인 접근은 로그인 유도 화면을 봅니다.
- 노트 전용입니다(폴더 공유 불가). 노트가 휴지통에 들어가면 링크는 열리지 않습니다(콘솔에 "중단됨"으로 표시).
- 관리자 콘솔 → 공유 링크에서 전체 링크를 조회하고 강제 취소할 수 있습니다. 무효 링크는 사유를 구분하지 않고 404로 단일화됩니다(토큰 추측 방지).

## 8. 감사 로그와 월간 리포트

모든 보안 관련 행위가 기록됩니다: 로그인 성공/실패, 가입·승인, 비밀번호 변경, 2FA 이벤트, 노트 생성·이동·삭제·복구·영구삭제, 노트 열람·내보내기, 첨부 추가·다운로드·삭제, ACL/역할/팀/공개 설정 변경, 공유 링크 생성·열람·취소, PII 처리, Redmine 토큰·조회, 정책 변경.

- **조회**: 행위자·행위·기간 필터 + 페이지네이션
- **CSV 내보내기**: 필터 결과 전체를 UTF-8(BOM) CSV로 다운로드
- **월간 리포트**: 연/월을 선택하면 점검표 5분류 리포트를 생성 — Markdown 저장 또는 인쇄(PDF)
- 감사 로그는 자동 삭제되지 않습니다. 보존 정책이 필요하면 DB 백업 후 수동 관리하세요.

## 9. 개인정보(PII) 점검

노트 저장 시 서버가 주민번호·카드번호 등 PII 패턴을 탐지해 표시합니다.

1. **개인정보 점검** 화면에서 탐지된 노트 목록 확인
2. 노트를 클릭하면 본문이 모달로 열리고 **탐지 라인이 포커스**됩니다 (열람은 `pii.view`로 감사 기록)
3. 처리: 작성자에게 **알림 보내기**(작성자는 접속 시 배너로 확인) / 작성자가 예외를 요청한 경우 **허용**(예외 처리) 또는 **반려**(사유 입력)
4. 예외 처리된 노트도 내용이 바뀌면 재탐지됩니다.

## 10. 업로드 정책

- **허용 확장자**: 칩 목록으로 추가/삭제. 기본 `png,jpg,jpeg,gif,webp,pdf,docx,xlsx,pptx,txt,md,csv,zip`
- **파일당 최대 용량**: MB 단위, 기본 25MB (서버 절대 상한 64MB)
- 정책 위반 업로드는 422로 거부되며 사용자에게 사유가 표시됩니다.
- **SVG는 스크립트를 포함할 수 있으므로 허용 목록에 넣지 않는 것을 권장합니다** (콘솔에도 경고가 표시됩니다).

### 고아 첨부 파일 회수 (선택 기능 — 기본 꺼짐)

첨부는 **파일을 먼저 쓰고 DB 행을 나중에 커밋**합니다. 쓰기 실패와 트랜잭션 롤백은 그 자리에서 정리되지만, **그 사이에 프로세스가 강제 종료되면**(kill -9, 전원 차단, OOM) DB에 행이 없는 파일이 디스크에 남습니다. 노트 삭제 시 파일 삭제가 실패한 경우도 같은 결과입니다. 이런 파일은 DB 기준으로 도는 purge가 영영 회수하지 못합니다.

회수기를 켜면 기동 60초 후, 이후 24시간 간격으로 이런 파일을 정리합니다(휴지통 purge와 동일한 배선).

```bash
WORKNOTE_ATTACHMENT_REAP_GRACE_HOURS=24   # 켬. 0(기본) = 끔
```

> #### ⚠️ 켜기 전에 — 이 설정은 "전용 디렉토리" 단언입니다
>
> **`WORKNOTE_UPLOAD_DIR`가 WorkNote 전용 디렉토리일 때만 켜세요.** 앱은 자기가 만든 샤딩 모양(`xx/yy/<32자리 16진수>`, 파일명이 앞 두 디렉토리로 시작)에 맞는 파일만 지우지만, **그 모양은 소유의 증명이 아닙니다** — MD5 기반 저장소의 흔한 레이아웃(`md5[0:2]/md5[2:4]/md5`)과 그대로 겹칩니다. 같은 디렉토리에 그런 저장소가 함께 있으면 **그쪽 파일이 삭제됩니다.**
>
> 앱은 이 전용성을 프로세스 안에서 확인할 방법이 없습니다(마커 파일도 마찬가지입니다 — 그런 저장소의 루트 역시 16진수 디렉토리만 들어 있어 우리 것과 구분되지 않습니다). 그래서 추측하지 않고 **운영자에게 묻는 방식**을 택했습니다. 켤 때마다 기동 로그에 전제가 다시 남습니다.
>
> ```
> INFO  고아 첨부 회수 활성(24시간 유예). 전제: /data/worknote/attachments 는 이 앱 전용 디렉토리입니다 — 다른 시스템의 파일이 섞여 있으면 삭제될 수 있습니다.
> ```
>
> 회수하는 누수는 강제 종료 중 업로드라는 드문 사건이라, **꺼 두었을 때의 비용은 디스크 파일 몇 개**입니다. 확신이 없으면 켜지 마세요.

켠 뒤의 동작:

- **유예 시간보다 최근에 수정된 파일은 건드리지 않습니다.** 커밋 직전의 업로드를 지우지 않기 위한 방어이므로 짧게 줄이지 마세요 — `6` 미만이면 기동 시 경고가 뜹니다
- **DB 행은 어떤 경우에도 삭제하지 않습니다.** 파일이 사라진 행은 개수만 WARN으로 남깁니다(실제 데이터 유실 신호이므로 백업을 확인하세요)
- 참조된 파일은 경로 문자열뿐 아니라 **파일 정체성(inode)** 으로도 보호됩니다 — DB 경로 표기가 비정규이거나 대소문자가 달라도 지워지지 않습니다
- 업로드 루트가 심볼릭 링크여도 정상 동작합니다(별도 볼륨 마운트 배치)
- 업로드 루트에 접근할 수 없는데 첨부 메타가 존재하면 별도 WARN이 뜹니다 — 볼륨이 빠졌다는 뜻입니다

```
INFO  고아 첨부 회수: 3건 1048576바이트           ← 정상 회수 (0건이면 로그 없음)
WARN  첨부 파일이 사라진 메타 2건 — 행은 그대로 둡니다(백업 확인 필요)   ← 조사 필요
WARN  업로드 루트에 접근할 수 없습니다: ... 첨부 메타 N건이 모두 열리지 않는 상태입니다   ← 즉시 조사
```

## 11. Redmine 연동 설정

1. 전제: `WORKNOTE_2FA_KEY` 설정(사용자 API 키 암호화에 사용)
2. 관리자 콘솔 → Redmine 연동: **활성화** 체크 + 서버 URL(예: `http://redmine.intra`) 저장
3. 이후 각 사용자가 프로필에서 **본인의 Redmine API 키**를 등록합니다. 등록 시 Redmine에 즉시 검증되며, AES-256-GCM으로 암호화 보관됩니다.
4. 조회는 각 사용자의 키로 프록시됩니다 — 서버 공용 계정이 없으므로 Redmine 측 권한이 그대로 적용됩니다.

## 12. 휴지통 보존 정책

- 삭제는 soft-delete입니다. 복구는 삭제한 본인 또는 관리자, 즉시 영구 삭제는 관리자만 가능합니다.
- 자동 영구 삭제 스케줄러: 기동 60초 후 첫 실행, 이후 24시간 간격. `WORKNOTE_PURGE_RETENTION_DAYS`(기본 30) 경과분을 삭제하고 첨부 파일도 함께 정리합니다. 실행 내역은 `who=system`, `act=node.purge`로 감사 기록됩니다.
- 0 이하로 설정하면 자동 삭제가 꺼집니다(휴지통 무제한 보존).

## 13. 백업과 복구

백업 대상은 두 개뿐입니다. **반드시 함께, 같은 시점에** 백업하세요(DB의 첨부 메타데이터와 디스크 파일이 어긋나면 안 됩니다).

| 대상 | 경로 |
| --- | --- |
| SQLite DB | `WORKNOTE_DB` (기본 `./worknote.db`) |
| 첨부 디렉토리 | `WORKNOTE_UPLOAD_DIR` (기본 `./attachments`) |
| 2FA 암호화 키 | `WORKNOTE_2FA_KEY` 값 자체 — 키가 없으면 복원해도 2FA·Redmine 등록 복호 불가 |
| TLS 키스토어 | `WORKNOTE_TLS_KEYSTORE`(`.p12`)와 비밀번호. 데이터는 아니지만 잃으면 재발급 절차를 다시 타야 합니다. **일반 백업과 분리해 암호화 보관** |

```bash
# 예시: 일 1회 스냅샷 (프로세스 실행 중에도 안전한 SQLite 온라인 백업)
# 저장 디렉토리는 700이므로 이 작업은 앱 실행 계정으로 돌려야 합니다 (앱 계정의 cron/systemd timer, 또는 sudo -u)
sqlite3 /data/worknote/worknote.db ".backup '/backup/worknote-$(date +%F).db'"
rsync -a /data/worknote/attachments/ /backup/attachments-$(date +%F)/
```

- 별도 백업 계정이 저장 디렉토리를 직접 읽는 구성이라면 [데이터 파일 권한](#데이터-파일-권한)의 "백업 계정이 그룹 권한으로 접근하고 있었다면"을 먼저 읽으세요 — `700` 적용 시 그 접근이 끊깁니다.
- 산출물(`/backup/...`)에는 평문 DB가 그대로 들어갑니다. 저장 위치의 권한과 보존 기간을 별도로 통제하세요.

- 보존 기간은 최소 `WORKNOTE_PURGE_RETENTION_DAYS` + 여유분을 권장합니다(실수 삭제 복구 여지).
- 노트에 개인정보가 포함될 수 있으므로 백업 자체의 암호화·접근 통제를 권장합니다.
- **복구**: 프로세스 중지 → DB 파일과 첨부 디렉토리를 같은 시점 백업으로 교체 → 기동. Flyway가 스키마 버전을 자동 확인합니다.

| 항목 | 정책 |
| --- | --- |
| 비밀번호 | 최소 10자, PBKDF2-HMAC-SHA256 120,000회 + 사용자별 salt |
| 세션 | 30분 무활동 만료, 로그인·2FA·비밀번호 변경 시 세션 ID 재발급(고정 공격 방어) |
| 세션 무효화 | 비밀번호 변경/초기화 시 해당 사용자의 다른 세션 즉시 무효화 |
| 쿠키 | `HttpOnly`, `SameSite=lax`, TLS 활성 시 `Secure` 자동 부여 |
| CSRF | 상태 변경 요청의 `Origin`(없으면 `Referer`) 검증. 프록시 TLS 종단 시 `WORKNOTE_CANONICAL_ORIGIN` 필수 |
| 저장소 파일 권한 | DB 부모 디렉토리·업로드 루트 `700`, DB 파일·첨부 `600`(첨부는 생성 시점 부여). server 모드는 `WORKNOTE_DB` 절대 경로 필수, 점검 실패 시 기동 중단(`WORKNOTE_STORAGE_STRICT=false`로 WARN 강등 가능) |
| 전송 구간 | 기본 HTTP. 사내 CA 인증서로 HTTPS 전환 가능(`WORKNOTE_TLS_ENABLED`+키스토어) |
| 가입 | 관리자 승인제 (승인 전 로그인 불가) |
| 2FA | TOTP(SHA1·6자리·30초), 시드 AES-256-GCM 암호화 보관, 오프라인 검증(외부 통신 0) |
| 2FA 강제 | 관리 능력 보유 계정은 유예(기본 7일, `app_setting`의 `2fa.grace_days`) 후 미등록 시 기능 차단 |
| 로그인 실패 | 계정 5회·같은 IP 30회 연속 실패 시 5분 자동 잠금(인메모리, 재기동 시 초기화). 잠금 전이는 `auth.lockout`, 실패 자체는 `login.fail` — 둘 다 모니터링 |
| 감사 | 인증·리소스·관리·공유·PII·연동 전 행위 기록, IP 포함 |

| 기동 실패: "저장소가 소유자 전용(700/600)임을 확인하지 못해 기동을 중단합니다" | server 모드 저장소 점검 실패. 메시지에 경로와 실행할 `chmod` 명령이 들어 있습니다. **chmod 전에 그 디렉토리가 앱 전용인지 확인**하세요 — 공용이면 이전이 답입니다 ([데이터 파일 권한](#데이터-파일-권한)). 생성·보정 자체가 실패한 경우라면 소유자를 앱 실행 계정으로 바꾸거나(`chown`) 마운트가 읽기 전용/비-POSIX인지 확인 |
| 기동 실패: "server 모드에서는 DB 경로가 절대 경로여야 합니다" | `WORKNOTE_DB` 미지정(기본 `./worknote.db`)이거나 상대 경로. 전용 디렉토리로 DB를 이전하고 절대 경로를 지정하세요 ([DB 이전 절차](#데이터-파일-권한)) |
| 첨부 디렉토리 용량이 DB 기록보다 계속 큼 | 강제 종료로 남은 고아 파일. 회수기는 **기본 꺼짐**입니다 — 업로드 루트가 앱 전용임을 확인한 뒤 `WORKNOTE_ATTACHMENT_REAP_GRACE_HOURS=24`로 켜세요 ([고아 첨부 파일 회수](#고아-첨부-파일-회수-선택-기능--기본-꺼짐)) |
| 로그: "첨부 파일이 사라진 메타 N건" | DB 행은 있는데 파일이 없는 상태 = 실제 데이터 유실. 회수기는 행을 지우지 않습니다. 첨부 디렉토리 백업 복원 여부를 확인하세요 |
| 로그: "업로드 루트에 접근할 수 없습니다" | 첨부 볼륨이 빠졌거나 `WORKNOTE_UPLOAD_DIR` 경로가 바뀐 상태 — 그동안 모든 첨부가 열리지 않습니다. 마운트를 즉시 확인하세요 |
| **아무도 로그인할 수 없음** (유일 관리자가 2FA 기기 분실 + SMTP 미설정) | 앱 실행 계정으로 데이터 디렉토리에 센티넬 파일을 놓아 복구하세요 — [최후 복구](#아무도-로그인할-수-없을-때--최후-복구break-glass) |
| 기동 실패: "브레이크글래스 복구: ..." | 센티넬 파일 내용 문제(사번 없음·비밀번호 10자 미만·알 수 없는 키 등) 또는 출처 검증 실패(파일·부모·**조상 경로**의 소유자·권한). 메시지가 원인 경로와 현재 소유자·권한을 지목합니다. 조치는 [최후 복구](#아무도-로그인할-수-없을-때--최후-복구break-glass)의 "거부 메시지를 조치할 때" 참조 — 공유 디렉토리라면 `chmod`가 아니라 **데이터 디렉토리 이전**이 답입니다. 파일은 남아 있으니 고쳐서 재기동하세요 |
| 기동 실패: "이전 복구 시도가 중단된 흔적이 있습니다: ....processing" | 재적용이 아니라 **중단**입니다. DB를 직접 열어 적용 여부를 확인한 뒤(위 [최후 복구](#아무도-로그인할-수-없을-때--최후-복구break-glass)의 조회 명령) 그 파일을 지우고 재기동하세요 |
| 업그레이드 후 백업이 실패하기 시작함 | 저장소가 `700`이 되어 백업 계정의 그룹 접근이 끊긴 상태. 백업을 앱 실행 계정으로 돌리거나 산출물만 넘기세요 ([데이터 파일 권한](#데이터-파일-권한)) |
| 공유 링크 호출이 404로 실패 (스크립트·연동) | `GET /api/share/{token}` 폐지 — 경로 자체가 없어져 404입니다(405 아님). `POST /api/share/{token}/view` 로 변경 ([API 변경](#업그레이드-시-api-변경--공유-링크-열람)) |
| 바꾼 뒤에도 403 `invalid_origin` | POST는 CSRF Origin 검증 대상입니다. 스크립트라면 `-H "Origin: <서비스 오리진>"`을 추가하세요(프록시 TLS 종단이면 `WORKNOTE_CANONICAL_ORIGIN`과 정확히 같은 값) |
| 기동 실패: 키스토어 관련(`Could not load store`, `password was incorrect`) | `WORKNOTE_TLS_KEYSTORE` 경로·읽기 권한, `WORKNOTE_TLS_KEYSTORE_PASSWORD`, `WORKNOTE_TLS_KEY_ALIAS`(변환 시 `-name` 값)를 확인 |
| TLS 전환 직후 로그인·저장이 전부 403 `invalid_origin` | 리버스 프록시가 TLS를 종단하는데 `WORKNOTE_CANONICAL_ORIGIN` 미지정. 브라우저 주소창의 오리진을 그대로 넣고 재기동 ([TLS 적용](#tlshttps-적용)) |
| TLS 전환 후 로그인해도 계속 로그인 화면 | 쿠키가 `Secure`인데 일부 경로가 HTTP로 접속되는 상태. HTTP 접근을 프록시에서 HTTPS로 리다이렉트하고, 브라우저 쿠키를 지운 뒤 재시도 |
| 2FA 설정 시 "2FA 키가 구성되지 않았습니다" (422) | `WORKNOTE_2FA_KEY` 미설정. Base64 32바이트 키를 넣어 재기동 |
| 복구 코드 메일이 안 감 | SMTP 미설정이거나 사용자 이메일 미등록. 콘솔에서 2FA 초기화로 대체 가능 |
| 관리자가 기능 차단됨 ("2FA 등록 필요") | 유예 기간 경과. 해당 계정으로 로그인해 2FA 등록하면 즉시 해제. 다른 관리자가 2FA 초기화로 유예 재부여도 가능 |
| 사용자가 접속했는데 흰 화면/로그인 루프 | 세션 만료는 정상 동작. 지속되면 브라우저 쿠키 삭제 후 재시도 |

| Redmine 키 등록 409 | Redmine이 키를 거부. 사용자에게 API 키 재발급 안내 |
| 편집 유실 우려(서버 장애 후) | 클라이언트가 미전송분을 보존·재전송함. 사용자에게 같은 브라우저로 재로그인 안내 |

### 로그 확인

표준 출력(stdout)으로 로그가 나갑니다. purge 실행 건수, 첨부 IO 실패, 2FA 키 오류, Redmine 통신 실패가 주요 항목입니다. 서비스 등록 시 stdout을 파일/저널로 수집하세요.
