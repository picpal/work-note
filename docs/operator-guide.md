## 1. 아키텍처 개요

```
┌─────────────── worknote-0.1.0.jar (단일 프로세스) ───────────────┐
│  Spring Boot 3.5 (내장 Tomcat, :8080)                            │
│  ├─ /            프런트엔드 정적 파일 (jar에 포함된 dist)          │
│  └─ /api/*       REST API (세션 인증 · 권한 엔진 · 감사)           │
│  Flyway ── 기동 시 스키마 자동 마이그레이션                        │
└──────────────────────────────────────────────────────────────────┘
        │                              │
   SQLite 파일                    첨부 디렉토리
   WORKNOTE_DB                    WORKNOTE_UPLOAD_DIR
   (기본 ./worknote.db)           (기본 ./attachments)
```

- 외부 의존 서비스 없음(CDN·외부 API 0). 폐쇄망에서 그대로 동작합니다.
- SQLite는 단일 라이터 특성상 커넥션 풀이 1로 고정되어 있습니다(`SQLITE_BUSY` 방지). 3~4팀 규모를 상정한 설계입니다.
- 데이터는 **DB 파일 + 첨부 디렉토리** 두 곳뿐입니다. 백업도 이 둘이 전부입니다.

## 2. 설치와 기동

### 요구사항

- Java 21 (빌드·실행)
- Node.js + pnpm (빌드 시에만)

### 빌드

```bash
cd frontend && pnpm install && pnpm build   # dist/ 생성 (jar에 포함됨 — 선행 필수)
cd ../backend && ./gradlew bootJar          # build/libs/worknote-0.1.0.jar
```

### 기동

```bash
# local 모드 (무인증 — 개인 PC용)
java -jar worknote-0.1.0.jar

# server 모드 (인증 + 권한 — 팀 공용)
WORKNOTE_MODE=server \
WORKNOTE_ADMIN_PASSWORD='10자-이상-초기-관리자-비밀번호' \
WORKNOTE_DB=/data/worknote/worknote.db \
WORKNOTE_UPLOAD_DIR=/data/worknote/attachments \
WORKNOTE_2FA_KEY="$(openssl rand 32 | base64)" \
java -jar worknote-0.1.0.jar
```

- server 모드 **최초 기동** 시 사용자가 0명이면 `admin` 계정(사번 `admin`, 역할 `admin`)이 `WORKNOTE_ADMIN_PASSWORD`로 자동 생성됩니다. 비밀번호가 비어 있으면 기동이 실패합니다(fail-secure).
- 이후 기동에서는 부트스트랩이 건너뛰어지므로 `WORKNOTE_ADMIN_PASSWORD`는 더 이상 필요 없습니다.
- **`WORKNOTE_2FA_KEY`는 한 번 정하면 바꾸지 마세요.** 이 키로 2FA 시드와 Redmine API 키가 암호화됩니다. 키를 바꾸거나 잃으면 기존 등록이 전부 복호 불가가 되어 사용자 전원이 재등록해야 합니다. 키 파일을 안전한 곳에 별도 보관하세요.

### 환경변수

| 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `WORKNOTE_MODE` | `local` | `local`(무인증) / `server`(인증+권한) |
| `WORKNOTE_DB` | `./worknote.db` | SQLite 파일 경로 |
| `WORKNOTE_ADMIN_PASSWORD` | (없음) | server 모드 **최초 기동 시 필수**. 초기 admin 비밀번호(10자 이상) |
| `WORKNOTE_UPLOAD_DIR` | `./attachments` | 첨부 바이너리 저장 루트 |
| `WORKNOTE_PURGE_RETENTION_DAYS` | `30` | 휴지통 보존 일수. 0 이하 = 자동 영구 삭제 끔 |
| `WORKNOTE_2FA_KEY` | (없음) | Base64(32바이트) AES-256 키. 2FA·Redmine 키 암호화에 사용. `openssl rand 32 \| base64`로 생성 |
| `WORKNOTE_SMTP_HOST` | (없음) | 2FA 복구 코드 메일 발송용 SMTP 서버. 미설정 시 복구 메일 기능 비활성 |
| `WORKNOTE_SMTP_PORT` | `25` | SMTP 포트 |
| `WORKNOTE_SMTP_FROM` | `worknote@corp.local` | 발신 주소 |
| `WORKNOTE_SMTP_USER` / `WORKNOTE_SMTP_PASSWORD` | (없음) | SMTP 인증 계정(필요 시) |
| `WORKNOTE_SMTP_STARTTLS` | `false` | STARTTLS 사용 여부 |
| `SERVER_PORT` | `8080` | HTTP 포트 (`--server.port=` 인자도 가능) |

고정 정책(환경변수 아님): 세션 타임아웃 30분, 멀티파트 업로드 상한 64MB(실 정책은 관리자 콘솔의 업로드 정책이 우선), 세션 쿠키 `HttpOnly` + `SameSite=lax`. TLS 종단을 두는 경우 `application.yml`의 `cookie.secure` 주석을 해제해 재빌드하세요.

## 3. 최초 설정 체크리스트

1. `WORKNOTE_2FA_KEY` 생성·보관 후 server 모드 기동
2. `admin`으로 로그인 → **즉시 2FA 등록** (admin은 유예 기간(기본 7일) 후 미등록 시 기능이 차단됨)
3. 관리자 콘솔 → **팀·스페이스**: 팀 생성, 최상위 폴더를 팀 스페이스로 지정
4. **역할 관리**: 필요 시 커스텀 역할 생성 (시스템 역할 3종은 수정 불가)
5. **업로드 정책**: 허용 확장자·용량 확인 (기본: png,jpg,jpeg,gif,webp,pdf,docx,xlsx,pptx,txt,md,csv,zip / 25MB)
6. (선택) SMTP 설정 — 2FA 복구 코드 메일 발송에 필요
7. (선택) **Redmine 연동** 설정
8. 백업 스케줄 구성 ([§13](#13-백업과-복구))

## 4. 사용자 관리

### 계정 수명주기

```
가입 신청(pending) ──관리자 승인──> active ──비활성화──> disabled
        └── 반려(비활성화 처리)          └── 재활성화 가능
```

- **가입 승인**: 관리자 콘솔 → 가입 승인 대기. 승인 시 기본 역할 **방문자**(읽기 전용)로 활성화됩니다. 승인 후 필요한 역할로 변경하세요.
- **직접 생성**: 사용자 관리 → 계정 추가(사번·이름·이메일·역할·초기 비밀번호).
- **비밀번호 초기화**: 사용자 관리에서 새 비밀번호 지정(10자 이상). 해당 사용자의 **다른 세션은 즉시 무효화**됩니다.
- **2FA 초기화**: 기기 분실 등으로 복구 메일도 못 받는 사용자용. 시드가 삭제되고 유예 기간이 다시 부여됩니다.
- **비활성화**: 로그인이 즉시 차단됩니다. 데이터는 유지됩니다.
- 실패한 로그인은 감사 로그에 기록되지만 **자동 잠금(lockout)은 없습니다** — 감사 로그의 `login.fail`을 주기적으로 확인하세요.

## 5. 권한 모델

> 원본 설계: [권한·디렉토리 설계 스펙](superpowers/specs/2026-06-10-worknote-권한-디렉토리-design.md)

**유효 권한 = 역할 상한(무엇을 할 수 있는가) ∩ ACL 범위(어느 리소스에서인가)**

### 역할 — 능력의 상한

| 역할 | 종류 | 능력(caps) |
| --- | --- | --- |
| 관리자(admin) | 시스템 | 모든 관리 + 리소스 능력 |
| 일반사용자(operator) | 시스템 | `res.read/edit/create/delete/export/share` |
| 방문자(visitor) | 시스템 | `res.read` |
| (커스텀) | 사용자 정의 | 아래 11종 조합 |

능력 11종 — 관리: `admin.users` `admin.permissions` `admin.roles` `admin.security` `admin.audit` / 리소스: `res.read` `res.edit` `res.create` `res.delete` `res.export` `res.share`

시스템 역할은 수정·삭제할 수 없습니다(콘솔에서 보기 전용). 역할이 없는 능력은 ACL로 아무리 허용해도 발휘되지 않습니다.

### ACL — 리소스의 범위

- 주체: 개인 / 팀 / 전체(`@all`), 종류: `read` / `edit` / `deny`
- **폴더에서 하위로 상속**되며, 노드 단위 deny로 구멍(카브아웃)을 냅니다.
- **deny 절대 우선**: 개인 grant로도 팀 deny를 뚫을 수 없습니다.
- **deny-sticky**: 조상에서 deny된 주체는 더 가까운 하위 allow로도 되살아나지 않습니다(deny 아래 재허용 없음).
- 다중 주체(개인+소속 팀들) 해석은 deny-우선 합집합입니다.

### 팀과 스페이스

- 팀은 **그룹**입니다(역할이 아님). 팀에 사용자를 넣고, ACL 주체로 팀을 지정합니다.
- 최상위 폴더를 **팀 스페이스**로 지정하면 소유 팀에 자동 grant됩니다. 스페이스 간 이동은 강한 노출 경고 대상입니다.

### 공개(public)

- 폴더에 public을 지정하면 하위로 캐스케이드되고, 노트 단위로 제외(exclude)할 수 있습니다. 새 노트는 기본 제외입니다.

### 이름·이동·권한의 관계

트리는 안정적 id 기반이라 **이름 변경은 권한에 무영향**, **이동은 위치의 상속을 따라감**입니다. 이동으로 열람 가능 집합이 바뀌면 사용자에게 사전 경고(move-preview)가 뜨고 감사에 남습니다.

## 6. 관리자 콘솔 화면 안내

`/admin.html` — `admin.users` 능력이 있는 계정만 진입할 수 있습니다.

| 화면 | 용도 |
| --- | --- |
| 대시보드 | 전체/활성/대기 사용자·팀 수, 승인 대기 목록, 최근 감사 활동 |
| 가입 승인 대기 | 가입 신청 승인·반려 |
| 사용자 관리 | 검색·필터, 역할 변경, 비밀번호 초기화, 2FA 초기화, 비활성화, 계정 생성 |
| 권한 관리 | 트리에서 노드 선택 → ACL 편집(주체·grant/deny), public 지정, 상속 항목 표시 |
| 역할 관리 | 역할 카드 목록, 커스텀 역할 생성·편집·삭제(시스템 역할은 보기 전용) |
| 팀·스페이스 | 팀 생성·이름 변경·삭제, 팀원 추가/제거, 최상위 폴더의 스페이스 지정 |

| 개인정보 점검 | PII 탐지 노트 목록, 본문 확인(라인 포커스), 예외 승인·반려, 작성자 알림 |
| 감사 로그 | 행위자·행위·기간 필터, CSV 내보내기, 월간 감사 리포트 생성 |
| 업로드 정책 | 허용 확장자·파일당 최대 용량 |
| Redmine 연동 | 연동 on/off, 서버 URL |
| 보안 설정 | 서버 고정 보안 정책 확인(읽기 전용) |

## 7. 공유 링크 관리

- 공유 링크는 **deny를 넘는 유일한 read 예외**입니다. 그 대신 만료(1~365일)·취소·열람 수 제한·대상 지정(사번 목록)이 있고 생성/열람/취소가 전부 감사 기록됩니다.
- **로그인은 여전히 필요합니다** — 링크는 권한의 예외이지 인증의 예외가 아닙니다. 비로그인 접근은 로그인 유도 화면을 봅니다.
- 노트 전용입니다(폴더 공유 불가). 노트가 휴지통에 들어가면 링크는 열리지 않습니다(콘솔에 "중단됨"으로 표시).
- 관리자 콘솔 → 공유 링크에서 전체 링크를 조회하고 강제 취소할 수 있습니다. 무효 링크는 사유를 구분하지 않고 404로 단일화됩니다(토큰 추측 방지).

## 8. 감사 로그와 월간 리포트

모든 보안 관련 행위가 기록됩니다: 로그인 성공/실패, 가입·승인, 비밀번호 변경, 2FA 이벤트, 노트 생성·이동·삭제·복구·영구삭제, 노트 열람·내보내기, 첨부 추가·다운로드·삭제, ACL/역할/팀/공개 설정 변경, 공유 링크 생성·열람·취소, PII 처리, Redmine 토큰·조회, 정책 변경.

- **조회**: 행위자·행위·기간 필터 + 페이지네이션
- **CSV 내보내기**: 필터 결과 전체를 UTF-8(BOM) CSV로 다운로드
- **월간 리포트**: 연/월을 선택하면 점검표 5분류 리포트를 생성 — Markdown 저장 또는 인쇄(PDF)
- 감사 로그는 자동 삭제되지 않습니다. 보존 정책이 필요하면 DB 백업 후 수동 관리하세요.

## 9. 개인정보(PII) 점검

노트 저장 시 서버가 주민번호·카드번호 등 PII 패턴을 탐지해 표시합니다.

1. **개인정보 점검** 화면에서 탐지된 노트 목록 확인
2. 노트를 클릭하면 본문이 모달로 열리고 **탐지 라인이 포커스**됩니다 (열람은 `pii.view`로 감사 기록)
3. 처리: 작성자에게 **알림 보내기**(작성자는 접속 시 배너로 확인) / 작성자가 예외를 요청한 경우 **허용**(예외 처리) 또는 **반려**(사유 입력)
4. 예외 처리된 노트도 내용이 바뀌면 재탐지됩니다.

## 10. 업로드 정책

- **허용 확장자**: 칩 목록으로 추가/삭제. 기본 `png,jpg,jpeg,gif,webp,pdf,docx,xlsx,pptx,txt,md,csv,zip`
- **파일당 최대 용량**: MB 단위, 기본 25MB (서버 절대 상한 64MB)
- 정책 위반 업로드는 422로 거부되며 사용자에게 사유가 표시됩니다.
- **SVG는 스크립트를 포함할 수 있으므로 허용 목록에 넣지 않는 것을 권장합니다** (콘솔에도 경고가 표시됩니다).

## 11. Redmine 연동 설정

1. 전제: `WORKNOTE_2FA_KEY` 설정(사용자 API 키 암호화에 사용)
2. 관리자 콘솔 → Redmine 연동: **활성화** 체크 + 서버 URL(예: `http://redmine.intra`) 저장
3. 이후 각 사용자가 프로필에서 **본인의 Redmine API 키**를 등록합니다. 등록 시 Redmine에 즉시 검증되며, AES-256-GCM으로 암호화 보관됩니다.
4. 조회는 각 사용자의 키로 프록시됩니다 — 서버 공용 계정이 없으므로 Redmine 측 권한이 그대로 적용됩니다.

## 12. 휴지통 보존 정책

- 삭제는 soft-delete입니다. 복구는 삭제한 본인 또는 관리자, 즉시 영구 삭제는 관리자만 가능합니다.
- 자동 영구 삭제 스케줄러: 기동 60초 후 첫 실행, 이후 24시간 간격. `WORKNOTE_PURGE_RETENTION_DAYS`(기본 30) 경과분을 삭제하고 첨부 파일도 함께 정리합니다. 실행 내역은 `who=system`, `act=node.purge`로 감사 기록됩니다.
- 0 이하로 설정하면 자동 삭제가 꺼집니다(휴지통 무제한 보존).

## 13. 백업과 복구

백업 대상은 두 개뿐입니다. **반드시 함께, 같은 시점에** 백업하세요(DB의 첨부 메타데이터와 디스크 파일이 어긋나면 안 됩니다).

| 대상 | 경로 |
| --- | --- |
| SQLite DB | `WORKNOTE_DB` (기본 `./worknote.db`) |
| 첨부 디렉토리 | `WORKNOTE_UPLOAD_DIR` (기본 `./attachments`) |
| 2FA 암호화 키 | `WORKNOTE_2FA_KEY` 값 자체 — 키가 없으면 복원해도 2FA·Redmine 등록 복호 불가 |

```bash
# 예시: 일 1회 스냅샷 (프로세스 실행 중에도 안전한 SQLite 온라인 백업)
sqlite3 /data/worknote/worknote.db ".backup '/backup/worknote-$(date +%F).db'"
rsync -a /data/worknote/attachments/ /backup/attachments-$(date +%F)/
```

- 보존 기간은 최소 `WORKNOTE_PURGE_RETENTION_DAYS` + 여유분을 권장합니다(실수 삭제 복구 여지).
- 노트에 개인정보가 포함될 수 있으므로 백업 자체의 암호화·접근 통제를 권장합니다.
- **복구**: 프로세스 중지 → DB 파일과 첨부 디렉토리를 같은 시점 백업으로 교체 → 기동. Flyway가 스키마 버전을 자동 확인합니다.

## 14. 보안 정책 요약

| 항목 | 정책 |
| --- | --- |
| 비밀번호 | 최소 10자, PBKDF2-HMAC-SHA256 120,000회 + 사용자별 salt |
| 세션 | 30분 무활동 만료, 로그인·2FA·비밀번호 변경 시 세션 ID 재발급(고정 공격 방어) |
| 세션 무효화 | 비밀번호 변경/초기화 시 해당 사용자의 다른 세션 즉시 무효화 |
| 쿠키 | `HttpOnly`, `SameSite=lax` (TLS 시 `secure` 활성화 권장) |
| 가입 | 관리자 승인제 (승인 전 로그인 불가) |
| 2FA | TOTP(SHA1·6자리·30초), 시드 AES-256-GCM 암호화 보관, 오프라인 검증(외부 통신 0) |
| 2FA 강제 | 관리 능력 보유 계정은 유예(기본 7일, `app_setting`의 `2fa.grace_days`) 후 미등록 시 기능 차단 |
| 로그인 실패 | 자동 잠금 없음 — 감사 로그(`login.fail`) 모니터링 필요 |
| 감사 | 인증·리소스·관리·공유·PII·연동 전 행위 기록, IP 포함 |

## 15. 트러블슈팅

| 증상 | 원인 · 조치 |
| --- | --- |
| 기동 실패: "WORKNOTE_ADMIN_PASSWORD 환경변수로 관리자 비밀번호를 지정하세요" | server 모드 최초 기동인데 초기 비밀번호 미지정. 환경변수를 넣어 재기동 |
| 기동 실패: frontend dist 없음 | `pnpm build` 없이 bootJar를 만든 경우. frontend 빌드 후 jar 재빌드 |
| 기동 실패: `Port 8080 was already in use` | 기존 프로세스 확인(`lsof -i :8080`) 또는 `--server.port=` 변경 |
| 2FA 설정 시 "2FA 키가 구성되지 않았습니다" (422) | `WORKNOTE_2FA_KEY` 미설정. Base64 32바이트 키를 넣어 재기동 |
| 복구 코드 메일이 안 감 | SMTP 미설정이거나 사용자 이메일 미등록. 콘솔에서 2FA 초기화로 대체 가능 |
| 관리자가 기능 차단됨 ("2FA 등록 필요") | 유예 기간 경과. 해당 계정으로 로그인해 2FA 등록하면 즉시 해제. 다른 관리자가 2FA 초기화로 유예 재부여도 가능 |
| 사용자가 접속했는데 흰 화면/로그인 루프 | 세션 만료는 정상 동작. 지속되면 브라우저 쿠키 삭제 후 재시도 |
| Redmine 조회 502 | Redmine 서버 통신 실패. URL·네트워크 확인 |
| Redmine 키 등록 409 | Redmine이 키를 거부. 사용자에게 API 키 재발급 안내 |
| 편집 유실 우려(서버 장애 후) | 클라이언트가 미전송분을 보존·재전송함. 사용자에게 같은 브라우저로 재로그인 안내 |

### 로그 확인

표준 출력(stdout)으로 로그가 나갑니다. purge 실행 건수, 첨부 IO 실패, 2FA 키 오류, Redmine 통신 실패가 주요 항목입니다. 서비스 등록 시 stdout을 파일/저널로 수집하세요.
