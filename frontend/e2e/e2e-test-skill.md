# e2e 테스트 작성 스킬 — 참고 노트

이번 work-note e2e 구축에서 검증된 것들을, 나중에 범용 "e2e 테스트 셋 생성 스킬"로 만들 때
그대로 옮겨 쓸 수 있는 형태로 기록한다. (성공/실패 판정이 끝난 것만 적는다 — 추측 금지)

## 스킬이 강제해야 할 절차 (순서 고정)

1. **화면 인벤토리 매핑을 코드에서 뽑는다** — 문서가 아니라. (이번 건: QA 문서가 "9스크린"이라 했지만 실제 코드는 12스크린이었다. 라우팅 코드(NAV 배열·해시 파싱)가 단일 진실.)
   - Explore 서브에이전트 1회로: 엔트리 목록, 화면별 컴포넌트, 네비게이션 방식, 셀렉터 후보, 인증/시딩 API, 기동 방법을 한 번에 수집.
2. **서빙 모드를 먼저 확정한다** — dev 서버와 프로덕션 빌드가 다른 기능 플래그로 뜨는 앱이 흔하다(이번 건: dev=localStorage 모드라 화면 절반이 안 뜸). "어떤 빌드가 실제 화면 전부를 노출하는가"를 스펙 작성 전에 결정.
3. **데이터 수명주기 결정**: 매 실행 DB 초기화 여부, 시드 계정, 시딩 경로(UI vs API). 초기화는 webServer 커맨드 안에서 한다 — globalSetup과 webServer의 실행 순서에 의존하지 않는 유일한 위치.
4. **인증 픽스처**: setup 프로젝트에서 UI 로그인 1회 → `storageState` 저장 → 본 프로젝트가 `dependencies: ["setup"]`으로 물고 시작. 비로그인 시나리오는 spec에서 `test.use({ storageState: {cookies:[],origins:[]} })`로 덮어쓴다.
5. **파일럿 1화면 → 전체 통과 → 재실행 1회 이상 통과**를 확인한 뒤에만 나머지 화면으로 확장한다. 재실행 통과 = DB 초기화·픽스처·직렬성이 전부 맞다는 증거.
6. **lessons.md 루프**: 스펙이 한 번이라도 그린이 아니었으면 원인을 lessons.md에 적고, 다음 spec 작성 전에 재독.

## 검증된 설계 결정

- **직렬 실행이 기본값** (`workers: 1, fullyParallel: false`): 단일 백엔드+단일 DB 공유 시 병렬은 상태 간섭으로 플레이크만 만든다. 병렬이 꼭 필요해지면 worker당 서버+DB를 띄우는 쪽으로 확장 (스킬에선 "느리면 나중에 병렬화"를 명시).
- **spec 단위 = 화면 단위**, 파일명 = 화면명. 화면이 크면(메인 에디터) 기능 영역으로 분할하되 디렉토리로 묶는다.
- **셀렉터 우선순위**: data-testid > role+접근성 이름 > placeholder/title > 텍스트+클래스 조합 > CSS 클래스 단독. testid가 없는 레거시 앱이라면 "동일 텍스트가 다른 역할로 중복되는지"를 반드시 확인(예: 전환 링크와 제출 버튼이 같은 문구).
- **assertion은 사용자 가시 결과로**: URL 변화·화면 문구·토스트. 내부 상태나 네트워크 응답은 보조로만.
- **재실행 가능성의 3원칙**: ① 서버는 테스트 러너가 띄우고 내린다(webServer) ② 상태는 매 실행 리셋 ③ 테스트가 만든 데이터는 유일 이름(타임스탬프 접미사).

## 스킬 패키징 제안

```
e2e-test-authoring/
  SKILL.md            # 위 절차 6단계 + 게이트(파일럿 재실행 통과 전 확장 금지)
  references/
    playwright.md     # config 골격(webServer·projects·storageState), 함정 목록
    pitfalls.md       # lessons.md 누적본 (vitest include 충돌, CSRF Origin, pnpm 승인 등)
  templates/
    playwright.config.ts
    start-server.sh   # "상태 리셋은 webServer 커맨드 안에서" 패턴
    auth.setup.ts
```

- SKILL.md에는 **절차와 게이트만**. 프레임워크별 코드는 references/templates로 분리 — 본문이 길면 모델이 절차를 건너뛴다.
- 스킬 입력으로 받을 것: 대상 URL/기동 커맨드, 시드 계정, "대표 화면" 지정(파일럿), 제외 화면.

## 이번 프로젝트 확정 사실 (스킬 예제 소재)

- Playwright 버전: @playwright/test ^1.62.1, chromium은 로컬 캐시 재사용.
- jar 기동 ~수 초, webServer timeout 90s면 충분. 헬스체크 URL: `/api/health` (무인증 허용 목록에 있어야 함).
- vitest와 공존: vite.config.ts `test.exclude`에 `e2e/**` 추가.
- 최종 규모: 16 spec + setup = 54 테스트, 전체 실행 ~20초(서버 기동 포함), 3연속 그린.

## 전체 확장 단계에서 추가 확정된 인사이트

### 공유 세션은 불변 자원이다 (이번 작업 최대 교훈)
setup이 저장한 storageState 세션을 "파괴"하는 경로가 두 번 독립적으로 사고를 냈다:
① 전역 request.newContext()가 storageState를 상속 → 같은 세션 id로 재로그인 → 서버 세션고정 방어가 id 회전 → 공유 쿠키 전면 무효. ② 로그아웃 테스트가 공유 세션으로 로그아웃 → 이후 spec 전멸.
스킬에 규칙으로 넣을 것: **"공유 세션을 변이시키는 시나리오(로그아웃·재로그인·비번 변경·2FA)는 반드시 빈 storageState 전용 컨텍스트에서 자체 로그인 후 수행"** + **함정은 경고 주석이 아니라 API 형태로 제거**(helpers의 apiLogin에 빈 storageState를 하드코딩).

### "단독 그린, 합주 레드"는 별도 검증 게이트다
그룹별(파일별) 통과가 전체 통과를 보증하지 않는다 — 공유 DB 누적 상태·세션 수명·실행 순서가 합주에서만 드러난다. 진단 기법: **실패 파일들의 알파벳 순서 비대칭**(특정 파일 이후만 전멸)이 세션/전역 상태 파괴자의 결정적 단서. 스킬 절차의 게이트를 "파일럿 재실행 → 그룹 재실행 → **전체 합주 2연속**" 3단으로.

### 병렬 서브에이전트 작성 워크플로 (효과 검증됨)
화면군 3분할 → 에이전트당 전용 포트(서버·DB·스토리지상태·리포트 경로를 전부 포트 스코프로 격리) → 각자 "작성→2연속 그린" 완료 → 리드가 lessons 병합 → 전체 합주 검증.
- 격리 파라미터화는 **에이전트 투입 전에** 하네스에 넣어야 한다 (.runtime-$PORT, admin-$PORT.json, test-results/p$PORT).
- 에이전트 보고서에 "실제로 틀렸다 고친 것"을 의무 항목으로 — 두 에이전트가 같은 함정에 독립적으로 빠진 것이 하네스 수정 근거가 됐다.
- 진행 중 도착한 교훈은 즉시 lessons.md에 병합 — 아직 작업 중인 에이전트의 같은 실수를 막는다.
- 전체 `pnpm e2e` 금지·자기 파일만 실행 규칙 필수 (타 에이전트의 미완성 spec이 섞인다).

### headless 특이사항
- OS 단축키(⌘/Ctrl+S)가 앱 window keydown까지 도달하지 않는 경우가 있다 → 같은 코드 경로의 가시적 UI(버튼)로 대체하고, 단축키 자체 검증은 스킬에서 "보증 불가" 항목으로 명시.
- 클립보드 API 검증 금지 — 값이 필요하면 생성 API 응답이나 DOM에서 획득.

### 시나리오 정확성
- 기능의 인증·접근 모델(로그인 필수 여부, ALLOWLIST)을 코드에서 확인한 뒤 기대를 써라 — "공유 링크는 공개"라는 통념이 이 앱에선 틀렸다(로그인 필수).
- 상태 의존 라벨(같은 섹션이 상태별로 다른 제목), 낙관적 UI(fire-and-forget 저장), 자동 등장 UI(유예 배너·PII 모달)는 spec 작성 전 렌더 분기 전체를 읽고 반영.
